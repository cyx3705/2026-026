# HistoryAurora 前端组件计划表 V1.0

> 制定日期：2026-08-19。依据是对 Janus / Mercury / Minerva / Diana 四个模块**注册页面**的
> 逐文件清点，不是设想。数字均可复算，复算方法见「调研方法」一节。
>
> 本表是历史资料：它记录 V1.0 决策时看到的事实。组件的现行清单与用法以
> `../package/HistoryAurora_组件清单与用法.md` 为准，长期约束以 `../current/技术合同.md` 为准。

## 一、调研结论（先说最反直觉的一条）

**不需要新建组件库——宿主已经有一套，而且模块在用。**

`HistoryVulcan.Shell/Themes/` 现有 2,044 行主题资源，其中 `ShellControls.xaml` 1,001 行提供
**16 个具名样式**，`ShellTokens.xaml` 提供 **65 个设计令牌**。三个有界面的模块合计引用了
**30 个不同的 `Shell.*` 键**。

真正的缺口是**家族不完整**：

| 家族 | 现有成员 | 缺失 | 后果 |
|---|---|---|---|
| `Shell.Segment.*` | Bar / Divider / Label / TextBox / ComboBox / Button / CheckBox（7 个） | **无 RadioButton / Toggle 成员** | Janus 自造 `OperationSegment`，一个 40 行 ControlTemplate |
| `Shell.Button.*` | Base / Accent / Danger / Ghost | — | 够用 |
| `Shell.GridHeader` / `Shell.Item.Base` | 表头 + 列表项 | 无「表格 + 详情」成对骨架 | 每页各自拼 Grid |

自造量的实测分布很能说明问题：

| 模块 | 自造具名样式 | 自造 ControlTemplate | 说明 |
|---|---|---|---|
| Janus | 1 | 4 | 全部集中在分段切换与表格单元 |
| Minerva | 1 | 0 | 单页工作区 |
| **Mercury** | **0** | **0** | **列表 + 详情两页，完全靠现有库拼成** |
| Diana | — | — | 无界面，纯管线模块 |

Mercury 零自造是最有力的证据：现有库**足以**支撑「列表 + 详情」这类主力页面。
Janus 的自造不是因为没发现库，而是因为它要的那个成员确实不存在。

## 四、组件计划

优先级依据：能消掉多少已发生的自造，以及有多少页面会立刻受益。

| 优先级 | 组件 | 形态 | 消掉的自造 | 受益页面 |
|---|---|---|---|---|
| **P0** | `Shell.Segment.Toggle` | RadioButton 样式，补全分段家族 | Janus `OperationSegment`（40 行 ControlTemplate） | projops（7 个 RadioButton） |
| **P1** | `Shell.Table` | ListView + GridView 骨架：表头、行、空态、选中 | Janus 表格单元样式 | overview / mcp / commanddetail / projops |
| **P1** | `Shell.Page.ListDetail` | 「左列表 + 右详情」页面骨架 | 各页自拼 Grid | mcp + commanddetail、overview |
| **P2** | `Shell.Toolbar` | 顶部按钮条（WrapPanel + Button.Ghost） | 各页自拼 StackPanel | 全部 7 页 |
| **P2** | `Shell.StatusLine` | 底部回执行（命令结果显示） | 各页自拼 Border + TextBlock | projops / mercury 管理页 |
| **P3** | `Shell.Form.Field` | 「标签 + 输入」成对布局 | 各页自拼 Grid 两列 | projops / github 连接 |

**不做**：`DataGrid` 主题化（用量 2 次，投入产出不成立）；新的图形/图表控件
（`GraphView` 的 417 行 cs 是自绘逻辑，与组件库无关）。

## 五、键名整体重构（DEC-005）

> 本节在 V1.0 定稿当天被改写。初稿主张保留 `Shell.*` 前缀以避免三个仓返工；
> 决策改为**借这次切出做一次性破坏性重构**。保留这段说明是为了记录判断的转向，
> 现行约束以 [`../current/技术合同.md`](../current/技术合同.md) REQ-UI-002 为准。

**65 个令牌 + 16 个具名样式全部从 `Shell.*` 改为 `Aurora.*`**，家族结构不变。
不提供别名、不设弃用期、不做双键并存。

改判的理由不是"返工代价小"，而是**别名本身就是要避免的技术债**：双键并存要求每个组件
维护两套键、每次演进同步两处，且无法判断某个模块实际用的是哪一套；"弃用期"在实践中
等于永久保留——三个模块各按自己节奏适配，没有力量促成最后一次删除。一次性断掉，
适配反而成为一件有明确完成标志的事。

**同时禁止模块自建组件**：模块 XAML 不得出现 `Style x:Key=` 与 `<ControlTemplate>`。

这条禁令有一个硬前置：**`Aurora.Segment.Toggle` 必须先落地**。本表第一节已经证明，
三个模块的全部自造（2 样式 + 4 模板）都源于这一个缺件。先断人后路再补路，只会逼出
更难发现的绕行写法。

### 必须配套的检查器

`DynamicResource` 找不到键时 WPF **不抛异常**，只是不套用该值——模块在适配前不会崩，
而是**静默退化成 WPF 默认外观**。静默失败比硬失败难发现得多。

因此重构必须同时交付一个可对**模块仓**运行的扫描器，报告三类问题：

| 检查项 | 模式 |
|---|---|
| 残留旧键 | `Shell\.[A-Za-z.]*` |
| 自建组件 | `Style x:Key=`、`<ControlTemplate` |
| 字面颜色 | `#[0-9A-Fa-f]{6}`、`Colors\.` |

目的是让"哪些模块尚未适配"成为可查询的事实，而不是靠肉眼看出哪一页变丑了。

## 六、调研方法（可复算）

```bash
# 工具窗口注册点
grep -rn "RegisterToolWindow" <模块仓> --include=*.cs

# 控件用量
grep -o '<[A-Z][A-Za-z]*' <各页面>.xaml | sort | uniq -c | sort -rn

# 模块引用了哪些宿主样式键
grep -rho "Shell\.[A-Za-z.]*" <各页面>.xaml | sort -u

# 模块自造了多少
grep -rho 'Style x:Key="[^"]*"' <模块仓> --include=*.xaml | wc -l
grep -rho '<ControlTemplate' <模块仓> --include=*.xaml | wc -l
```

## 七、本表未覆盖的问题（留给 B 阶段）

- **`copyexample` 名实不符**：实测该命令的域已被宿主改写为 `aurora`，但名字仍是
  `vulcan.command.copyexample`。改名 `aurora.command.copyexample` 属 Vulcan 侧 DEC-050，
  需与本仓协同落地。
- **`IUiModule` / `IShellUiAware` 契约本身要不要改**：本表只清点了模块**如何用**这两个接口，
  没有评估接口是否该收口。Vulcan DEC-049 已声明界面契约最终会删除，接口形态另议。
- 组件的**交互行为**（键盘导航、焦点顺序、无障碍）本次未清点。
