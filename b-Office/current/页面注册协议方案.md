# 页面注册协议方案 V1.0

> **状态：三节全部已实施（见 [技术合同](技术合同.md) REQ-UI-003），本文是其设计依据。**
>
> 背景见 [有效决策](有效决策.md) DEC-007（Aurora 登记进注册表）与 DEC-005（模块不得自建组件）。

## 为什么要换

今天模块注册页面走的是宿主声明的接口（`IShellUiRegistrar` / `ToolWindowDescriptor`，
都在 `HistoryVulcan.Core`），Aurora 只是运行期实现方。四条消费通道里只有一条受编译器保护：

| 通道 | 编译期检查 | 失败形态 |
|---|---|---|
| 接口实现 | 有 | 编译错误 |
| `ContentFactory` 返回值（`Func<object>`，Core 不依赖 WPF） | **无** | 运行期异常 |
| `DynamicResource Aurora.*` | **无** | **静默退化成默认外观** |
| pack URI 直连 `/HistoryAurora;component/…` | **无** | 运行期 `IOException` |

第四条只有 Mercury 有（3 个 XAML 文件），因为它对具名样式用了 `StaticResource`，
必须在解析期取到值。它靠程序集**短名**解析，工程文件里没有任何引用——
2026-08-20 的重名事故就是从这条把 Mercury 两个页面带崩的。

改走总线后，四条塌缩成一条：模块不再写 XAML，不再需要 `UseWPF=true`，
「模块不得自建组件」从禁令变成结构上不可能。

## 一、协议

### 1.1 传输：模块只连宿主，不认识 Aurora

模块的 `IModuleContext` 已经持有完整 `CommandBus`，调 `aurora.*` 与调自己的命令没有区别。
**模块不需要引用 Aurora 的任何程序集，也不需要知道它是否在运行。**

- 归属：命令在 `aurora` 域，由 Aurora 实现——这是模块间调用
- 传输：模块只有宿主总线这一个连接，宿主只路由不解释载荷
- 未连前端时 `FrontendExecutor` 为 null，总线**返回明确失败结果，不等网络超时**（现成行为）

### 1.2 方向：Aurora 拉取，宿主不缓存

Aurora 连上宿主后主动拉：

```
1. vulcan.module.list                  → 模块清单（现成命令）
2. 对每个 manifest 声明 ui = true 的模块：
   <域>.ui.describe                    → 该模块的页面描述 JSON
3. Aurora 按描述建页
```

**宿主不持有页面描述。** 这是本方案里最重要的一条负向决定，依据是实测教训：

`web.frontendcatalog` 就是"宿主缓存 + 前端连上时重放"的做法——

```csharp
_cachedCatalogs[normalized.FrontendName] = normalized;   // 按客户端名做键
_settings.Set(KeyFrontendCatalog, JsonSerializer.Serialize(...));   // 落盘
```

启动时无条件恢复，只有 32 条上限，**没有任何按存活性的回收**。前端改名一次，
旧目录就成了幽灵：`vulcan` 域至今报 66 条而实际应为 30。

页面注册若照抄，幽灵会从"命令数不准"升级成**界面上多出一个打不开的页面**。
拉取模型让注册成为派生状态，没有缓存可失效；代价只是 Aurora 启动时多一轮往返，
而模块本来就活在宿主进程里。

### 1.3 生命周期

| 事件 | 处理 | 是否需要新机制 |
|---|---|---|
| Aurora 启动 / 重连 | 重新拉取全量 | 否 |
| 宿主重启 | 模块重新 Attach，Aurora 重连后重拉 | 否 |
| 模块内容变化 | 模块调 `aurora.ui.invalidate owner=<域>`，Aurora 重拉该模块 | 否（上行走总线） |
| **模块装载 / 卸载** | 宿主须通知 Aurora | **是，见下** |

> **更正（2026-08-20）：本节初稿写「下行通知是唯一要新建的东西」，那是错的——
> 该机制已经端到端存在，是我写草案时没找到。** 保留这段记录，因为教训在于
> 「先查再建」：链路完整，缺的只是一个订阅者。

实际链路：

```
宿主模块集合变化
  → ServiceComposer: modules.ReloadCompleted → web.PublishModuleRevision(n)
  → 网关广播 {"type":"moduleRevision","revision":n}
  → Aurora: ShellServiceClient.ModuleRevisionReceived
  → App: ReloadUiModulesFromServiceAsync → host.ReloadConfirmedSources
  → Aurora 的 ModuleHost.ReloadCompleted
  → ModulePageLoader.ReloadAsync()
```

它恰好满足本协议对下行通知的要求：**Aurora 收到后只需重拉，不需要理解事件内容**，
宿主因此仍然不解释 UI 语义——它发的是「模块修订号变了」，不是「有哪些页面」。

`vulcan.module.*` 的字面量中继（DEC-043）是另一件事，管的是卸下同名 UI 快照，本协议不依赖它。

### 但它会连打好几遍

真机实测一次冷启动打了**三遍**（12:32:07 / :11 / :15）：ModuleHost 初次装载一次，
moduleRevision 通知引发的 `ReloadConfirmedSources` 又各一次。目前每遍都是空拉所以无害，
等模块真有页面时就是三倍 describe 调用与三轮建撤抖动。

因此 `ReloadAsync` **合并重入请求**：已在跑时只置脏标记，跑完补一轮，
所以最后一次请求的结果一定被反映。三次调用合并成两趟。

### 1.4 命令清单（v1）

| 命令 | 实现方 | 性质 | 说明 |
|---|---|---|---|
| `<域>.ui.describe` | 模块 | readonly | 返回本模块全部页面描述 |
| `<域>.ui.data` | 模块 | readonly | 组件取数据；带 `page` / `view` / 分页与筛选参数 |
| `aurora.ui.invalidate` | Aurora | standard | 模块声明自己的描述已变，请求重拉 |

**三条一律硬排除出 MCP。** 它们是界面内部协议，对模型无意义，且 `ui.data` 会产生大量条目——
参照 `McpExposurePolicy.HardExclusionReason` 里 `vulcan.command.run` 的做法，
在策略里写死原因，而不是依赖各模块自觉标注。

### 1.5 失败与隔离

- 某模块 `ui.describe` 失败或超时：**只跳过该模块**，记 Warn，其余照常建页
- 描述里引用了不存在的组件：该处渲染为显式占位（见 §2.5），**不得静默省略**——
  静默省略正是今天 `DynamicResource` 的失败形态，本方案的目的之一就是消灭它
- 描述 schema 版本不被支持：整个模块跳过并明确报版本号

## 二、描述 schema v1

### 2.1 组件集按实测频次定，不凭空设计

对三个模块 12 个页面的全部 XAML 做了控件频次统计：

```
TextBlock 66 · Grid 42 · Button 42 · GridViewColumn 34 · ColumnDef 26 · TextBox 20
StackPanel 19 · Border 16 · ListView 13 · MenuItem 12 · DockPanel 12 · ComboBox 10
WrapPanel 8 · RadioButton 7 · DataTemplate 7 · GridView 5
```

v1 组件集覆盖上表，不多做：

| 组件 | 覆盖的原生控件 | 实测支撑 |
|---|---|---|
| `stack` / `grid` | StackPanel / Grid / DockPanel / WrapPanel / Border | 97 处 |
| `text` | TextBlock / Run | 75 处 |
| `button` | Button | 42 处 |（1.8.14 退役为页面节点，改由面板承担）
| `table` | ListView + GridView + GridViewColumn + DataTemplate | 59 处 |
| `input` | TextBox | 20 处 |（1.8.14 退役为页面节点）
| `select` | ComboBox / ComboBoxItem | 21 处 |（1.8.14 退役为页面节点，改由面板 `mode: "select"`）
| `toggleGroup` | RadioButton | 7 处 —— **即缺件 `Aurora.Segment.Toggle`** |
| `menu` | MenuItem | 12 处 |

`toggleGroup` 之所以在 v1 里，是因为 Janus 的 `OperationSegment` 自造样式正是为它而生；
它同时是 DEC-005 解禁的前置。

弹窗不是 v1 页面组件。`aurora.ui.dialog` 是独立的宿主能力（REQ-UI-004），
不要把 `type: "dialog"` 写进页面描述——渲染器会把它当成缺件占位。

### 2.2 交互分两类——这是 schema 的核心判断

实测：12 个页面共 **53 个 `Click=` + 9 `SelectionChanged=` + 8 `Checked=` +
6 `TextChanged=` + 2 `MouseDoubleClick=`，而 `Command=` 出现 0 次**。
47 个处理器里**只有 15 行碰总线**。

也就是说，**约三分之二的交互不是在调命令**，而是在做本地视图工作：
筛选列表、切换重命名态、展开树节点、更新状态文字。

所以 schema **不能**把交互一律映射成命令。那样会逼模块新增几十条只在 UI 内有意义的命令，
污染注册表与命令域，还要逐条判 MCP 暴露。分两类：

| 类别 | 归谁 | 是否产生命令 |
|---|---|---|
| **视图行为**：筛选、排序、选中、展开、翻页、就地编辑态 | **组件自理** | 否 |
| **外部副作用**：写文件、提交、转换、复制到剪贴板、打开窗口 | 模块 | 是，声明命令模板 |

判据：**这个动作离开这个页面还有没有意义**。有 → 命令；没有 → 组件行为。
按这条，实测 47 个处理器里约 15 个是真命令，与"碰总线的 15 行"吻合。

### 2.3 数据不内联

表格数据不写进描述，描述里只声明数据源；组件按需调 `<域>.ui.data` 取，
并把分页/筛选/排序作为参数传回。理由：Mercury 命令集实测 199 行，
内联会让每次重拉都搬一遍全量。

### 2.4 形状

```json
{
  "schemaVersion": 1,
  "owner": "HistoryMercury",
  "pages": [
    {
      "id": "mcp",
      "title": "命令集",
      "placement": {
        "side": "center", "ratio": 1.0,
        "tabTarget": null, "visible": true, "singleton": true
      },
      "content": {
        "type": "stack", "orientation": "vertical", "gap": "tight",
        "children": [
          {
            "type": "table",
            "id": "commands",
            "dataSource": { "command": "mercury.ui.data", "args": { "view": "commands" } },
            "columns": [
              { "key": "name",    "title": "命令",  "width": 240 },
              { "key": "domain",  "title": "域",    "width": 90  },
              { "key": "summary", "title": "说明",  "width": "*" }
            ],
            "view": { "filterable": true, "sortable": true, "selection": "single" }
          },
          {
            "_退役": "1.8.14 起 button 不再是页面节点，本例仅存历史形态，勿照抄",
            "type": "button",
            "text": "复制示例",
            "style": "accent",
            "enabledWhen": { "selected": "commands" },
            "invoke": {
              "command": "aurora.command.copyexample",
              "args": { "name": { "from": "commands.selected.name" } }
            }
          }
        ]
      }
    }
  ]
}
```

要点：

- `placement` 与现有 `ToolWindowDescriptor` 字段 1:1——那部分本来就是纯数据，无需重新设计
- `view` 里的 `filterable` / `sortable` / `selection` 本意是**组件行为**，不产生命令。
  **但截至 1.9.0 它们没有任何实现**——声明了、解析了，全仓没有一处读它
  （REQ-UI-054）。这正是本协议要消灭的失败形态，只不过这次是协议自己犯的。
  在拍板「实现还是删除」之前，不要写这一项
- `invoke` 才是命令，参数可从视图状态取值（`from`）
- 1.13.0 起表格列可写 `cellAction` 动作 id。非空格子以按钮语义触发，动作占位符默认读取
  被点行同名字段；缺失动作必须显示断链诊断（REQ-UI-068）
- 没有任何地方出现样式键或颜色。**模块不得指定外观**，只能选 `style` 的语义档位
  （`accent` / `ghost` / 默认），具体长相由 Aurora 决定——这是 DEC-005 的直接落地

### 2.5 缺件不得自建，但必须有出口

模块需要的组件不存在时：**渲染为显式占位**，标出缺件名，并计入可查询的缺件清单。

不允许两件事：模块自建组件（DEC-005），以及静默省略（那会退回今天的失败形态）。
占位让"哪些页面在等哪个组件"成为可数的事实，而不是靠肉眼发现某一页变丑。

> 组件申请与排期规则见「组件申请通道」——**本草案未写该节**。


## 三、组件申请通道

「模块不得自建组件」是硬禁令（DEC-005），因此模块被缺件卡住时**必须有一条非自建的出口**，
否则禁令只会被绕过——自建版本一旦上线就不会有人回来删。Janus 的 `OperationSegment`
就是现成的例子：它自造了一版分段 Toggle，已经在跑。

### 两个来源，一本账

| 来源 | 命令 | 说明 |
|---|---|---|
| **用出来的** | 无需调用 | 页面描述引用了未支持的组件，渲染成占位的同时自动记一笔 |
| **提出来的** | `aurora.ui.request` | 还没写进页面、但已知需要的组件 |

自动进账的那类最可信——它来自真实使用，不是设想。显式申请用于提前排期。

```bash
aurora.ui.request component=segment.toggle reason="分段家族缺 Toggle 成员"
aurora.ui.requests    # 列出未交付的
```

### 三条设计约束

**申请必须落盘。** 会话内的缺件清单（`aurora.ui.missing`）重启即失，那样的"通道"
没人能据以排期。台账写进设置键 `aurora.ui.componentrequests`。

**已交付的自动出账，判据是渲染器。** `PageRenderer.SupportedComponents` 是
「是否已交付」的**唯一权威**，台账不另存一份状态——两边各存会各说各话。
有一条契约测试专门防这条漂移：遍历受支持集合逐个渲染，任何一个渲染成占位就失败。
漂移的表现很隐蔽——申请刚提就被自动出账，而页面上仍是占位。

**同一组件只占一条，但页面清单累积。** 排期看的是波及面，不是提交次数；
首个提出方保留，不被后来者覆盖。

### 没有写进来的：优先级与兑现时限

本节只做**通道**，不定排期规则。谁排期、多久兑现、按什么排序，是承诺而不是技术，
留给使用方决定。台账提供的是事实：谁要、用在哪几页、什么时候第一次提的。

## 四、实施记录（2026-08-20）

Aurora 侧已落地：`b-Code-Studio/Shell/Pages/`（描述模型与解析、渲染器、拉取器）
与 `BuiltinCommands.Pages.cs`（三条命令）。17 条契约测试覆盖上面两节的每条要求。

施工中定下的两条细节，原草案没写：

**取数载荷同时放 `Message`。** `CommandResult.Data` 是 `object?`，跨进程中继后
结构化载荷不会原样存活。因此协议要求同一份 JSON 也出现在 `Message` 里，
渲染器优先读 `Data`、回退 `Message`。不这样做的话，模块装在宿主进程时能用、
装在 Aurora 进程时也能用，唯独跨进程取数会静默拿到空表。

**间距不走 `DynamicResource`，画刷与文字样式走。** 间距令牌在浅色深色里取值相同
（PadTight=8 / Pad=12），不随主题变化；而 `Thickness` 资源是四边统一值，
用作 `Margin` 会给纵向栈额外撑出左右缩进。主题相关的部分仍然必须是 `DynamicResource`。

实测：三条命令注册成功，`aurora.ui.reloadpages` 返回「问了 0 个模块，建了 0 页」——
目前没有任何模块提供 `ui.describe`，这是预期结果，不是故障。
`vulcan.command.list mcp=visible domain=aurora` 返回 0 条。

> **补记（2026-08-20）**：§1.4 要求的硬排除已在宿主侧落地——
> `McpExposurePolicy.HardExclusionReason` 按后缀排除 `<域>.ui.describe` / `<域>.ui.data`，
> 按名排除 `aurora.ui.reloadpages` / `invalidate` / `missing`。
> 此前它们不可见只是**策略**结果（走前端注册路径 `PolicyVisible=false`），
> 网关策略一改就可能翻转；`vulcan.command.run` 正是这样从前端搬到服务侧后自动变可见的。
>
> 排查时别用 `vulcan.mcp.schema` 判断暴露面——它列的是**可投影**清单
> （全量减硬排除，实测 192/202），不是实际暴露的 97 条。我第一次就是看错了这个数。

## 五、未决问题

1. **下行通知的具体形状**（§1.3）——唯一要新建的机制
2. **`ui.data` 的分页与筛选参数约定**：谁定义筛选语法，模块还是组件
3. **就地编辑**（Mercury 的 `IsRenameMode`、Minerva 的表格编辑）算视图行为还是命令，
   实测是"编辑态是视图行为、提交是命令"，但需要 schema 明确表达提交时机
4. **Janus 图谱**：按"不允许自绘"，它是一张组件申请单（提交 DAG 视图），
   不是本协议的例外；但它是 v1 组件集**唯一无法覆盖**的现存页面，
   优先级需要在组件申请那节里定
5. **schema 版本演进**：文本协议没有编译器保护，需要自己的兼容规则
