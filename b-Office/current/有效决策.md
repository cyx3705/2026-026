# HistoryAurora 有效决策

## DEC-010 弹窗用自绘顶栏；进程内确认走 Aurora 而不是 WebSocket 中继

- 状态：已接受
- 日期：2026-08-20
- 决策：
  1. `AuroraDialogWindow` 使用 `WindowStyle.None` 与 `WindowChrome`，顶栏用
     `Aurora.WindowButton.Close`，与主窗体同一套令牌，不露出系统标题栏。
  2. 进程内界面把宿主 `CommandBus.Confirmation` / `ConfirmationRouter` 接到
     `MessageBoxConfirmation`。`ShellRelayConfirmation` 在 `ConnectedShells=0`
     时直接拒绝，不适合 Aurora 已装在同一进程、没有 WebSocket Shell 的形态。
- 原因：1.1.0 弹窗仍用系统标题栏，和主界面脱节。Janus 改名等写操作只靠
  `ConfirmPrompt`，进程内会被静默拒绝，表现为“弹窗没了、无法改名”。
- 替代条件：若将来恢复独立前端进程并保证 Shell 已连接，中继确认可以重新作为默认通道，
  但仍应保留进程内这条直连，避免再出现无框失败。

## DEC-009 弹窗由 Aurora 自持，独立 Window 必须自带主题字典

- 状态：已接受
- 日期：2026-08-20
- 决策：三条——
  1. 弹窗是 Aurora 的组件，不是模块自己的 `Window`。种类固定为
     `message` / `confirm` / `prompt` / `content`，入口是 `AuroraDialogWindow` 与
     `aurora.ui.dialog`；
  2. 弹窗窗口在构造时合并与主窗体同一套令牌，**不依赖** `Application.Current.Resources`，
     也不从 `ShellWindow.Resources` 继承——后者对顶层 Window 根本不可达；
  3. 弹窗不是停靠页，不进入 `PageRenderer.SupportedComponents`。页面描述协议管的是
     工具窗口，弹窗是另一条宿主能力。
- 原因：前端独立并把界面装进宿主进程后，模块对话框（Janus 的
  `HistoryPreviewDialog` / `RollbackMessageDialog`，以及系统 `MessageBox`）全部退化。
  根因不是键名改了，而是独立 Window 找不到令牌：`DynamicResource` 找不到键时不抛异常。
- 本轮边界：只交付 Aurora 侧组件并把关于框/危险确认/MCP 远程确认切过来。
  模块仓的对话框下一轮再改编，避免把「做组件」和「改三个模块」混成一次。
- 替代条件：只有证明「顶层 Window 能稳定继承主窗体资源」的同级决策可以替代。

## DEC-008 界面回归模块形态，独立 exe 退役

- 状态：已接受
- 日期：2026-08-20
- 裁决原文：「如果有 exe 文件的话，别单独发，我们从逻辑上也把他视为一个模块。启动什么的
  都按照注册的指令跑，别多一个 exe 暴露。（如果可以，更好的结果是这个程序还是没有 exe）
  还是依靠宿主，至于桌面快捷打开什么的都是 mercury 桌面活动坞的功能。」
- 决策：四条——
  1. Aurora **没有独立 exe**。界面是宿主装载的一个模块，在宿主进程内开窗；
  2. 启动与显隐一律走注册的指令，不再有第二个可执行文件暴露给用户；
  3. 发布只有**一个包**，就是模块包；
  4. 桌面快捷入口归 Mercury 活动坞，它调指令而不是指路径。
- 与 DEC-004 的关系：**推翻其第 1、2 条**。DEC-004 判「模块路径到不了那个进程」，
  证据采自**双角色 exe 时代**——那时模块命令落在服务进程、界面在另一个进程。
  4.0.0 之后只剩一个进程，那条推理的前提已不存在。
  DEC-004 的第 3 条（自持命令注册表）与第 4 条（Core 解冻）继续有效。
- 支持这次改判的实测：`Shell` 的 10,678 行几乎不依赖 `Application`——全仓仅一处
  `Application.Current` 且**本就空值守卫**，`App.xaml` 一个字典都没合并，
  主题全挂在 `ShellWindow.Resources` / `DockManager.Resources` / 浮动窗口上。
  界面代码早就是窗口作用域的，`Application` 实例接近摆设。

### 施工中撞到的四个障碍，以及后来怎么热重载

**一、可回收上下文 + WPF 不能「先装新再卸旧」。** 冷启动仍会重载 2–3 次。旧实现用
`pinned: true` 把 Aurora 钉进 `AssemblyLoadContext.Default`：不卸载、静态字段跨重载存活、
`EnsureStarted` 做幂等。代价是更新界面必须重启宿主，DLL 也被 Default 锁死。
现行做法：manifest **不再 pinned**。宿主整体 Reload **先 DestroyUi 并卸载旧可回收 ALC，再 Build**。
Aurora 的 `DestroyUi` 关掉窗口、停 Dispatcher、Join STA 线程。冷启动多轮重载会闪一下窗口，
这是可接受的；未改包 SHA 时复用 ALC 是后续优化，不是本轮范围。

**二、XAML 按程序集简单名走默认上下文。** 第一次实现用不可回收自定义 ALC，
`ShellWindow.InitializeComponent()` 在 `ResourceDictionary.DeferrableContent` 上抛
`XamlParseException：类型引用无法找到 {…;assembly=AvalonDock.Themes.VS2013}`。
钉住路径的补丁是 `LoadFromAssemblyPath` 进 Default——那正是卸不掉的原因。
现行热重载路径：默认上下文的 `Resolving` **只返回**可回收 ALC 里已经装好的程序集，
绝不把它们装进 Default。`pinned: true` 仍保留给真正不能拆的模块。
残余风险：WPF 的 `PropertyMetadata`、pack URI 表、未完成的 Dispatcher 操作可能继续
抓住 Type，使旧 ALC 实际卸不干净。那是泄漏，不是第二扇窗——只要旧 Resolving 已摘掉，
新解析只看当前 ALC 集合。

**三、宿主进程要拿到 WPF 运行时。** WPF 是共享框架，模块自带不了；宿主 `runtimeconfig`
里没有 `Microsoft.WindowsDesktop.App` 就直接 `FileNotFoundException`。
宿主 App 工程因此加了 `<FrameworkReference Include="Microsoft.WindowsDesktop.App.WPF" />`——
**只加框架引用，不开 `UseWPF`**：宿主工程仍然零界面代码、零 XAML 编译、没有 App.xaml，
REQ-A8「宿主不引用 WPF」在源码层面继续成立。变的是运行时前提：
**本进程从此要求机器装有 WindowsDesktop 运行时**。这是"界面住进宿主"的必要代价。

**四、宿主的模块 UI 生命周期跑在非 STA 线程上。** 模块一建控件就抛"调用线程必须为 STA"，
而该异常被按模块吞掉——表现为某个模块的页面悄悄少一个，别的模块照常，日志里只有一条 Warn。
`ModuleHost.CreateUi` 经 `IShellUiRegistrar.Invoke` 编组到界面线程。
`IShellUiProvider.DestroyUi` **不得**再走 `Invoke`：提供方要在服务线程上 Join 自己的 STA 线程。
其它 UI 模块仍 `Invoke`，且必须在提供方关机之前拆完。

### 新增的宿主契约

`IShellUiProvider`：由模块**反向提供**界面注册器。与 `IShellUiAware` 方向相反——
界面整体成为模块之后，宿主自己不再持有任何界面实现，注册器只能来自模块。
宿主在 `CreateUi` 阶段先取遍提供方再分发给消费方：模块装载顺序不可控，
靠目录名排序碰巧让提供方排在前面是不能依赖的。

`ServiceComposer` 的 `EnableUiModules` 由 false 改为 true。这不会让宿主长出界面：
没有模块实现 `IShellUiProvider` 时 `ShellUi` 保持 null，`CreateUi` 整段跳过，
进程仍是纯无头的。

### 验收（2026-08-20 真机实测）

宿主进程内 `aurora.ui.windows` 返回 7 个窗口：console / modules（框架）、
overview / graph / projops（Janus）、dock.manager（Mercury）、historyminerva（Minerva）。
域分布 aurora 40 / diana 29 / janus 36 / mercury 26 / minerva 9 / vulcan 32。
进程列表里**只有 HistoryVulcan.exe 一个**。

### 未尽项

- `vulcan.app.show` 等冷启动路径仍指向宿主自身可执行文件（4.0.0 起等同再起一个无头服务）。
  界面进程内之后这条应改为"叫醒本进程内的窗口"，尚未改。
- Mercury 的管理页注册在 `StaticResourceExtension` 上报过一次警告，待逐页复核。
- 宿主快照（`z-Publish/host`）尚未刷新，Aurora 目前靠 `Directory.Build.user.props`
  指向未发布的宿主构建输出联调。

- 替代条件：只有证明"界面必须与服务分属两个进程"的同级决策可以替代。

## DEC-007 Aurora 登记进 Vulcan 注册表，不因是应用而免登记

- 状态：已接受
- 日期：2026-08-20
- 裁决原文：「模块注册应该指的是注册在 vulcan 里面的，aurora 既然是前端就模块应该注册在
  vulcan 里面而不算宿主，否则特殊模块太多了；页面注册应该走的是模块间调用而不算模块
  寄生在宿主内」。
- 决策：三条——
  1. Aurora 在 Vulcan 的模块注册表里**有平级身份**，在「模块管理」中与 Diana / Janus /
     Mercury / Minerva 并列显示，不因为它恰好是承载模块的那个进程而免于登记；
  2. 宿主之所以是宿主，只因为它持有指令总线与注册表本身。**前端不属于宿主**；
  3. 页面注册的目标形态是**模块间调用**（模块调 Aurora 的页面契约），而不是模块经宿主的
     模块契约声明窗口。
- 与 DEC-004 的关系：**不冲突，各管一段**。DEC-004 管的是命令投递路径——实测证明前端命令
  无法经「装载进服务进程的模块」投递（`DataDirectory` 会变、够不到 `ShellWindow` 与 UI 线程），
  该结论继续成立。DEC-007 管的是注册表身份。二者同时为真：Aurora 是应用进程，
  同时在注册表里是一个 `MainClassType = null` 的模块条目。
- 为什么不按进程边界发特例：特例会累积。「承载模块的进程不登记」这条规则一旦成立，
  下一个同时是应用又是模块的东西就要再判一次，而判据（谁装载谁）与注册表要回答的问题
  （体系里有哪些部件）无关。
- 实施发现：Aurora 仓的 Module 工程**从来没有 `ModuleInfoBase` 子类**，因此它编出的 DLL
  根本不会被宿主识别为模块（宿主按基类全名 `BaseVariable.ModuleInfoBase` 做鸭子类型识别，
  MD-02），只会被当成普通依赖库。此前能出现在模块管理里的 `HistoryAurora 0.2.0` 是一个
  **孤儿二进制**——它有 `ModuleInfo` 与 `Commands.ConsoleCommandGroup`，
  但 `git log --all -S` 在本仓搜不到任何一处对应源码。
- 施工约束（两条互相牵制，缺一即错）：
  1. 模块程序集名必须是 `HistoryAurora.Module` 而非 `HistoryAurora`。与 App 同名会在同进程内
     遮蔽 pack URI 的资源解析——WPF 按程序集**短名**解析 `/HistoryAurora;component/…`，
     App 有 `.g.resources` 而模块没有，先命中模块就找不到主题。实测表现为 AvalonDock 抛
     `IOException 找不到资源 themes/auroratheme.baml`，主界面停靠浮动层失效，且编译期零征兆。
  2. 因此 `ModuleInfo.ModuleName` 必须**显式覆写**回 `HistoryAurora`。基类默认取程序集名，
     而 ModuleName 同时就是指令域名；不覆写会让域从 `aurora` 漂成别的值。
- 未尽项：页面注册仍是「模块经宿主声明窗口」的旧形态（日志可见 `模块 X 的窗口 Y 声明中央区`）。
  改为模块间调用需要先有 Aurora 侧的页面描述契约，属于 C 阶段，本轮未动。
- 替代条件：只有证明「承载模块的进程不能同时是注册表条目」的同级决策可以替代。

## DEC-006 命令随实现方改域，撤销「迁入不得改名」

- 状态：已接受
- 日期：2026-08-19
- 决策：迁入 Aurora 的命令一律从 `vulcan.*` 改为 `aurora.*`，与 HistoryVulcan DEC-050
  「指令域跟随实现方，不跟随历史归属」一致。撤销 REQ-UI-001 中「迁入不得改变命令名」一条。
- 依据（实测，非孰先孰后）：`vulcan.command.copyexample` 迁出后，其域**已经**被宿主按
  REQ-CMD-011 强制改写为 `aurora`，而名字仍是 `vulcan.command.copyexample`——
  当前正处于「域是 aurora、名是 vulcan」的名实不符状态。REQ-UI-001 描述的「只变注册方、
  其余不变」是一个运行时不存在的状态，它不是被推翻的，是本就没成立过。
- 否决的另一条路：让宿主放弃对模块命令域的强制改写以保住原名。代价是 REQ-CMD-011
  的全局一致性——「模块域由 owner 强制」是所有模块共用的规则，为一个应用破例会让它失去意义。
- 施工约束：39 条前端命令**逐条判定，不一刀切**。判定标准沿用 DEC-050：真实依赖 UI
  （`RequiresUiThread`、`Clipboard`、窗口、对话框）的随 Aurora 改域；只依赖总线、设置、
  数据根的归服务侧并保留 `vulcan.*`。
- 发布约束：与组件键名改名（DEC-005）**同批发布**。两次破坏性变更分两批放出，
  等于让三个模块适配两轮——合批是这次唯一能省下的返工。
- 替代条件：只有取消「模块域由 owner 强制」的同级决策可以替代。

## DEC-005 组件键名整体改为 `Aurora.*`，模块不得自建组件

- 状态：已接受
- 日期：2026-08-19
- 决策：借前端切出这次机会做**一次性破坏性重构**，三条同时生效：
  1. 全部设计令牌与具名样式从 `Shell.*` 改为 `Aurora.*`（65 个令牌 + 16 个样式）；
  2. **不提供 `Shell.*` 别名、不设弃用期、不做双键并存**；
  3. 模块 XAML **不得出现 `Style x:Key=` 与 `<ControlTemplate>`**，界面一律走组件库。
- 为什么不保留别名：别名本身就是技术债。双键并存意味着每个组件维护两套键、每次演进同步
  两处，且无法判断某个模块实际用的是哪一套；而"弃用期"在实践中等于永久保留——三个模块
  各按自己的节奏适配，没有任何力量会促成最后一次删除。一次性断掉，反而让适配成为一件
  有明确完成标志的事。
- 为什么禁止模块自建组件：实测三个模块共自造 2 个具名样式 + 4 个 ControlTemplate，
  且全部源于同一个原因——分段家族缺 Toggle 成员（见
  [前端组件计划表V1.0](../history/前端组件计划表V1.0.md)）。自造版本不跟随主题演进，
  最终表现为"只有这一页长得不一样"。禁止自造的前提是**组件库先补齐**，
  因此 `Aurora.Segment.Toggle` 是解禁的前置条件，不是可选项。
- 已知代价（明确接受）：`DynamicResource` 找不到键时 WPF **不抛异常**，只是不套用该值。
  模块在适配前不会崩，而是**静默退化成 WPF 默认外观**。静默失败比硬失败难发现，
  因此必须配一个可执行检查器（见 REQ-UI-002），让"哪些模块尚未适配"成为可查询的事实，
  而不是靠肉眼看出哪一页变丑。
- 兼容立场：模块在切出完成后反过来做适配更新；本仓不为此排期、不保留过渡机制。
- 替代条件：只有证明"键名必须与提供方产品名解耦"的同级决策可以替代。

## DEC-004 Aurora 是独立应用，不是模块；宿主前端整体切出

- 状态：已接受
- 日期：2026-08-18
- 决策：四项定案——
  1. Aurora 是**独立应用** `HistoryAurora.exe`，不是被服务装载的模块；
  2. 宿主**彻底无 WPF**，危险命令确认中继到 Aurora；
  3. Aurora **自持命令注册表**并经既有 IPC 上报，沿用今日前端机制；
  4. **开掉 Core 冻结**，宿主走 **V4.0**，模块契约借此收口。
- 决策 1 与 3 的依据（实测，非推演）：把 `vulcan.command.copyexample` / `run` 改由模块注册后，
  命令名虽保住，但宿主强制把域改写为 `aurora`、来源改写为 `module`，且模块命令只落在**服务
  进程**——`DataDirectory` 从 `%AppData%\HistoryVulcan\` 变成服务根，相对路径脚本失效。
  前端命令依赖 `ShellWindow`/`ConsoleView`/UI 线程，模块路径根本到不了那个进程。
  该次试验已回退，不留在代码里。
- 决策 2 的依据：`WebGateway.RequestWebConfirmation` 与 `/api/confirm` 今天已存在但不可达
  （宿主 DEC-045 未尽项）。宿主无头化正好把这条挂空的通道接上，一举两得。
- 原因：宿主的既定方向是只保留指令总线与 MCP。前端是唯一一块体积大（12,712 行）、
  与总线和 MCP 都无耦合、且能整体移出的部分；而 `Services`/`ServiceHost` 本就不引用 `Shell`，
  唯一的结是 `App.xaml.cs:301` 那一处调用。
- 施工方案：见 [前端切出迁移方案.md](前端切出迁移方案.md)。
- 替代条件：只有当界面被证明必须与服务同进程时，本决策才失效。

## DEC-001 界面能力独立成模块，而不是留在宿主

> **已被 DEC-004 取代。** 本条主张把界面做成宿主装载的模块；实测证明模块命令只能落在服务
> 进程且会被改写域名，无法承载前端能力。保留本条仅为记录判断过程，不再作为依据。

- 状态：已接受
- 日期：2026-08-18
- 决策：新建 2026-026-HistoryAurora，承接 HistoryVulcan 前端进程当前自持的窗口、布局、
  控制台与主题能力。宿主最终只保留指令总线与 MCP。
- 依据（3.13.0 实测，非估算）：`vulcan` 域 81 条注册命令中，39 条来源为

  全为 false——零条投影为 MCP 工具，却占着服务进程注册表近一半条目，并参与每次 schema

- 替代条件：只有当界面能力被证明必须与宿主进程同生命周期时，本决策才失效。
