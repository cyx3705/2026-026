# HistoryAurora 有效决策

## DEC-033 每一格只留一页；Ctrl 标签态靠轮询按键

- 状态：已接受
- 日期：2026-09-11
- 版本：1.20.1
- 关联：REQ-UI-096 ～ 098、REQ-UI-100；**扩展 DEC-032 第 3 条**（顶栏只留一页 → 每一格只留一页）
- 背景：用户真机试 1.20.0：不是登记在中央的页拖进主窗口，只有顶栏顶掉旧页，别的格子照样攒多页、互相抢；
  按住 Ctrl 不出标签，只能继续用顶栏页签拖；顶栏页签拖出去仍是不收起的悬浮窗。
- 决策（用户拍板）：
  1. **每一格只留一页**。原话：「侧边栏底边栏之类的窗口统一设置为仅保留一个页面，其他页面均隐藏」。
  2. **标签态先于退役顶栏**。原话：「不应该再用顶栏的页签去控制窗口，而是按住 CTRL 每个窗口抽象显示出自己的页签
     （即页面原本内容消失整体页面居中显示自己的标签，这个标签可控制页面）」。
  3. **顶栏页签拖出也要收起**（用户说本轮重要性不大）：做法是卸掉 AvalonDock 的原生页签拖动——
     页签平时只换页，标签态下的页签拖动走 Aurora 会话，落空收起。
- 为什么 Ctrl 改轮询：WPF 只在 Aurora 的窗口拿着键盘焦点时收得到按键，用户要拖页面时焦点多半还在别的程序。
- 为什么要「等位」：登记不抢位，而同一批热重载里先占位的外来页随即被场景藏掉；不等位，那一格就空着、本场景的新页也不露面。
- 为什么模块场景里本模块页优先于常驻页：场景首访要露的是这个模块的工作面；常驻页在别的场景照样露面。
- 后果：Janus 场景里控制台被「图」顶掉（二者同一格），要看控制台从右栏胶囊打开；
  模块往已有页的一格登记，默认藏着等位；`aurora.ui.dock pos=tab` 等于换掉目标那一格的页。
- 替代条件：同 DEC-032——顶栏删除之后重判主文档区还要不要页签行。

## DEC-032 顶栏退役先转移后删除；场景只是显隐

- 状态：已接受
- 日期：2026-09-11
- 版本：1.20.0
- 关联：REQ-UI-094 ～ 099；**部分取代 DEC-031**（决策 1 的「页面集合」与「为什么命令集常驻」两段）
- 背景：顶栏最终要整个删掉。它今天还背着窗口控制组、页面拖出的起手点、工具页的 ▼ ✕ 三件事，
  先把这些转移走，顶栏本身下一步再删。
- 决策（逐条为用户拍板）：
  1. **场景不拥有页面**。原话：「场景本身就是页面启动和隐藏产生的区别，我们不弄不同场景附属不同页面的抽象，
     所有场景不对应显示和隐藏的页面，而是场景本身只显示和隐藏页面而已」。页面集合、增补剔除、断链账删除，
     `aurora.scene.add / remove` 一并删除（用户选了「删掉」而不是「改成显隐」）。
  2. **窗口控制组搬进右栏顶部**：导航栏从左搬到右，这样控制组仍在整个窗体右上角；右栏下半放常用页面胶囊，
     拖出胶囊经蓝色停靠控件嵌进场景。
  3. **顶栏只保留最后拖入的页签**：顶栏既然要退役，就不再允许它里面有多页。被顶掉的页只是隐藏。
  4. **命令集解除锚点、仍常驻**：DEC-031 的替代条件就此成立。
  5. **页面拖动不附着在页签上**：单独按住 Ctrl 约 0.3 秒，所有页面不显示内容、变成可拖的标签。
  6. **拖出去没落到停靠点就隐藏**：「悬浮页面很少独立使用」。
  7. **先删工具页右侧的 ✕ 与下拉菜单**，其余顶栏部件本轮只转移。
- 为什么被顶掉、被拖出的页都是「隐藏」而不是「移出场景」：场景已经不拥有页面，没有「移出」这回事；
  隐藏记在当前场景的布局里，别的场景不受影响。
- 为什么拖出落空要先摆回默认位置再隐藏：AvalonDock 隐藏一页时记住的「上一个容器」就是那个浮窗，
  下次显示会回到一个已关掉的浮窗里。
- 为什么 Ctrl 要按住 0.3 秒、而且单按才算：一按就进的话，控制台里每次 Ctrl+C / Ctrl+V 整个界面都会闪成标签。
- 后果：`aurora.scene.add / remove` 从注册表消失，模型侧调用会得到「未知指令」；
  1.19.0 存下的多页顶栏布局启动时只留上次选中的那一页；拖出落空的页从右栏「常用页面」再拖回来。
- 替代条件：顶栏删除之后，REQ-UI-096 的「只留一页」随顶栏一起消失，届时重判主文档区还要不要页签行。

## DEC-031 主页面按场景组织，场景布局即按模块名的命名布局

> **1.20.0 起部分被 DEC-032 取代**：「场景含页面集合」与「命令集因锚点而常驻」两条不再成立，其余照旧。

- 状态：已接受
- 日期：2026-09-10
- 版本：1.19.0
- 关联：[场景与导航方案](场景与导航方案.md)、REQ-UI-084 ～ 089、DEC-022（快捷键归 Mercury）、DEC-024（布局只存稳定 ID 与几何）
- 背景：全局页签条同时是窗口外框、全局导航与场景内切换三件事。模块越多它越长；
  同体量的 Janus 与 Minerva 在它下面走成了三页协同与一页收纳两个极端，
  用任何一个时其它模块的页都挂在眼前。
- 决策：
  1. **场景是主页面的组织单位**。切场景换掉整个停靠布局，不在场景里的页不出现。
     每个模块自动得到一个场景，模块一行代码不用改。
  2. **场景布局就是命名布局，名字是场景 id，模块场景的 id 是模块名**（用户拍板）。
     「命名布局」与「场景各记各的布局」因此是同一件事，不另开一种文件。
  3. **`aurora.scene.go` 对模型开放**（用户拍板）：「切到 Minerva」是一次 MCP 调用。
  4. **导航器的全局快捷键走 `mercury.hotkey.register`**（用户拍板；Mercury 已有该接口，未新增）。
     默认 `Ctrl+Alt+K`：这是全局键，抢 `Ctrl+K` 等于在浏览器与每个编辑器里拿走它。
  5. **场景膨胀只靠搜索 + 频次**（用户拍板），不做场景管理页——那又是一份要人维护的目录。
- 为什么命令集常驻：它是主文档区的锚点，窗口按钮栏挂在那个窗格的页签行上，
  藏掉它会被 `EnsureCentralWorkspace` 当场放回。这不是想要的形态，是拆顶栏之前的约束。
- 为什么先加后删（顶栏本版不动）：先删顶栏，中间会有一段没有任何导航入口。
- 后果：页签只剩当前场景的页，全局页签条事实上已退出「全局导航」；
  它剩下的窗口外框职责留给 REQ-UI-091。窗体左侧多出 128 宽的导航栏。
- 替代条件：若拆顶栏时发现命令集可以不当锚点，常驻集缩回只有控制台。

## DEC-030 启动期建页等宿主通知，不等定时器

- 状态：已接受
- 日期：2026-09-04
- 版本：1.17.0
- 关联：宿主 DEC-057（装载次序与就绪屏障）
- 背景：界面的启动困境是它自己解不了的——`Attach` 里开的 STA 线程立刻要去问各模块要页面，
  而那一刻宿主还在装别的模块。1.16.0 之前用「注册表安静 150ms」当判据，但装载期间注册表
  本来就安静，猜测必然有落空的时候。宿主日志里的证据是冷启动 140ms 内连着几次
  `vulcan.command.list` 都只看到 37 条框架指令。
- 决策：登记 `aurora.host.ready`，宿主装完全部模块后按命令名通知，界面在钩子里做整轮重拉；
  防抖定时器降为兜底，不删。
- 为什么不是「界面自己多等一会儿」：等多久取决于装了几个模块、每个模块多大，
  这两个数界面都不知道，而且会随运行区变化。**把一个宿主知道、界面不知道的时刻做成
  一条命令，比让界面猜得更久更准。**
- 为什么不抬宿主下限：钩子没有用到任何新的宿主公开面。5.1.2 及以前不认识这条命令，
  它就只是注册表里多出的一条，永远不会被调用——旧宿主上行为与 1.16.0 逐字一致。
  抬下限会把一次纯增量的改动变成一次强制升级。
- 后果：`DiscoverModuleSurfacesAsync` 改为返回 `PageLoadReport?`，就绪回执因此报得出
  问了几个模块、建了几页。调用点只有防抖定时器一处，无其它影响面。

## DEC-029 层由目录规定，命名空间跟目录走

- 状态：已接受
- 日期：2026-09-03
- 补充：DEC-018、REQ-UI-049
- 决策：
  1. `Shell/` 下建五个层目录 `0-Neutral` / `1-Base` / `2-Components` / `3-HostedPages` /
     `4-Composition`，根部不留散文件。序号即层号，序号后那一段即命名空间里的层名。
  2. **命名空间跟着目录走**：`Shell/2-Components/Panels/` 里的文件声明
     `HistoryAurora.Shell.Components.Panels`。
  3. 层的定义从 `LayerContractTests` 的两张硬编码表里删掉，改由目录树推导；
     `csproj` 一层一组 `Include`，成为比测试更早的第一道闸。
  4. `Shell/Properties/AssemblyInfo.cs` 移到 `Module/Properties/`：它是程序集元数据，
     本来就不属于任何一层，留在 `Shell/` 只会逼出一条「没有层的例外」。
- 原因：1.9.0 把三层写进合同时，目录是平铺的，层号写在测试里。这带来两个后果，
  第二个是致命的：
  1. **看目录看不出层。** 新人（和 AI）加文件时没有任何提示告诉他这一层不该认识那一层。
  2. **门禁看不见短名引用。** 所有散文件同在 `HistoryAurora.Shell` 一个命名空间下，
     跨层引用写成 `Selection.SelectionChannels`、`FrontendCommandCatalog.Source`
     就能靠外层命名空间就近解析，而门禁的正则只认 `HistoryAurora.Shell.<目录>` 全限定形式。
     于是三处真实的反向依赖在门禁全绿的情况下活了很多版：基础层的 `MessageBoxConfirmation`
     `is ShellWindow` 问装配根要主题；基础层的 `ShellTopBarCoordinator` 在交互控件清单里
     列着组件层的 `AuroraOptionBox`；页面层两处登记命令时引用装配根的
     `FrontendCommandCatalog.Source`。**它们是在命名空间带上层名的那一刻，
     由编译器一次全部报出来的**——不是查出来的。
- 三处的修法都是把方向倒过来，不是加 using：
  - 主题：基础层新增 `IThemedWindow`，`ShellWindow` 实现它，弹窗只拿到一个 `bool`；
  - 交互控件：基础层新增标记 `IInteractiveCommandControl`，`AuroraOptionBox` 自己实现，
    基础层的清单里不再出现任何组件类型；
  - 来源标记：`"framework:frontend"` 是中立事实，下沉为 `Neutral.FrontendCommandSource.Name`，
    装配根的 `FrontendCommandCatalog.Source` 改为转发。
- 替代方案与放弃原因：只挪目录、命名空间不动——那样目录能看出层，但门禁仍旧看不见短名引用，
  上面那三条今天仍会是绿的。分层的价值全在门禁真的拦得住，看得见而拦不住等于没有。
- 后果：版本 `1.16.0`。103 个文件换了落点，`Shell/` 下 18 个命名空间全部改名，界面行为零变化；
  构建产物的 `.g.resources` 资源名逐条不变，pack URI 一行未改。

## DEC-028 选项框右键菜单由控件自己开，不抢焦点也不挂 ContextMenu 属性

- 状态：已接受
- 日期：2026-09-02
- 补充：DEC-025
- 决策：
  1. `AuroraOptionBox` 右键**不再 `Focus()`**。选项菜单自己会拿键盘焦点，控件不必在它前面插一脚。
     左键那条路仍然要 `Focus()`——那里没有菜单，键盘接着用得上。
  2. 菜单是**独立实例、手动打开**，不挂到 `FrameworkElement.ContextMenu` 上；
     `Placement` 取 `Bottom`。右键**抬起**也要 `Handled`。
  3. 最近一次打开的菜单经 internal `OptionsMenu` 暴露给门禁，用来验「三项都在、选中那一项打着勾」。
- 原因：刚导入零件之后第一次右键没反应，先左键点一下、之后右键才有效。那一拍里连着发生三件事——
  控件拿焦点、菜单打开、菜单把键盘焦点收走。菜单是 `StaysOpen = false` 的，控件那次迟到的焦点变更
  一落地它就判自己失焦、当场关掉；等控件已经有焦点了（左键点过一次），`Focus()` 成了空操作，
  菜单就活下来了，于是看起来像「先左键才能右键」。挂在 `ContextMenu` 属性上则是第二条开菜单的路径：
  WPF 的 `PopupControlService` 会在右键抬起时按属性再走一遍，两条路径撞在一起就是「菜单闪一下就没了」。
- 后果：版本 `1.15.0`。`AuroraOptionBoxContractTests` 改为断言 `ContextMenu` 为空、`OptionsMenu` 非空。

## DEC-027 页面自己要的取数与回写不是用户动作

- 状态：已接受
- 日期：2026-09-02
- 补充：DEC-025、REQ-UI-045
- 决策：
  1. 页面表格取数（`PageRenderer.FetchAsync`）与面板候选取数（`PanelView.Options`）改走宿主
     `CommandBus.InvokeAsync` **安静通道**：不回显、不入历史、不触发 `Executed`。
     失败照常写日志；另留一条 `Debug` 级痕迹，用来在排障时回答「这一页到底取过数没有」。
  2. **程序回写控件值期间，控件的提交动作必须闭嘴。** `aurora.ui.panelset`（P-07）、跟随通道回填
     与候选重取三条路径统一经 `PanelView.WriteBack` 打标记，`SelectionChanged` 见到标记直接返回。
  3. 标记用 `try/finally` 恢复，不是改完再清：回写会同步引发 `SelectionChanged`，
     处理器里任何一个异常都会把标记永久留在开着的位置，从此这个面板再不提交任何东西。
- 原因：
  - 一次用户动作会连带触发本页全部表格重取。Minerva 属性整备改一格材料，控制台就多出五对
    「minerva.ui.data view=parts」「✓ Minerva 零件」，十行里没有一行是用户想看的，
    真正的结果反倒被顶出屏幕。宿主早就为这类高频内部调用留了安静通道，问题不在延迟而在语义：
    那些调用不是「操作」。
  - 回写不是用户的编辑，把它当编辑发出去会形成回环：模块按表格算出「这一列不统一」回写成
    「（不写）」，控件反手把「（不写）」当成一次用户选择提交回模块，于是整表被清空——
    用户看到的是自己什么都没点，材料却没了。
- 后果：版本 `1.15.0`，宿主下限不动（`InvokeAsync` 在 5.1.0 的 Core 冻结面里）。
  这是 HistoryMinerva 4.9.0 DEC-059「（不写）」批量框语义与 DEC-060 控制栏收声的前提。
  `PageProtocolContractTests` 由「取数回显一条」改为**一条都不该有**；
  `CellActionContractTests` 相应只数单元格动作那一条。

## DEC-026 控制台日志快照由 Aurora 生产、Diana 消费

- 状态：已接受

- 决策：Aurora 在控制台实际使用的 `MemoryShellLog` 唯一缓冲上提供隐藏只读

## DEC-025 模块只声明交互语义，单元格、弹窗与图标由 Aurora 统一实现

**2026-08-31（1.13.0）。** 表格状态与 z 目录入口采用列级 `cellAction`，继续绑定模块动作 id，
点击时从被点行解析参数；多选场景统一走 `aurora.ui.dialog kind=choice` 并返回候选 value；面板图标

## DEC-024 布局持久化只保存稳定 ID 与几何，不序列化停靠框架对象

**2026-08-31（1.12.20）。** `XmlLayoutSerializer` 依赖 `XmlSerializer` 为 AvalonDock 类型生成代码；
这些类型随 Aurora 位于可回收 ALC 时，运行时拒绝让非可回收生成程序集引用它们，因此模块化之后布局目录
一直为空。持久化改为 Aurora 自有的版本化 JSON：只遍历当前模型并投影成纯数据，恢复时再用当前版本描述符
和内容工厂重建模型。格式不承诺复刻框架私有状态，承诺的是用户可见的分栏、页签、浮窗、自动隐藏与隐藏位置。

文件使用原子替换，`layout.placements` 继续独立保存并承担损坏、缺页和延迟注册回退。聚焦还原继续使用原
`LayoutRoot`，避免把短暂的单页布局写入磁盘；浮窗因卸下旧根失效时，只从纯数据快照重建浮窗节点。

否决继续使用 XML 或反射框架私有字段：前者在真实模块上下文必然失败，后者把格式绑到 AvalonDock 私有实现，
会让一次依赖升级变成用户布局静默损坏。蓝色停靠覆盖层和拖动会话不属于持久化实现，本决策禁止顺带修改。

## DEC-023 转换内容下拉必须提交，来源选择指令必须展开占位符

**2026-08-31（1.12.19）。** `mode: select` 的文本框只把值发到选择通道，不跑 `commitAction`；`sourcePicker` 的 `selectCommand` 也不展开 `{selection.*}`。Minerva 属性整备页面已经切过去，选来源仍按默认零件文件夹打开目录对话框。下拉变更必须立即提交 `{value}`；选择指令里的占位符必须按当前通道展开，且替换值按指令语法加引号（「属性整备（改名）」含空格）。

## DEC-020 控制面板的行改成一等结构，orientation / inline / required 一并退役

**2026-08-29（1.9.2，破坏性）。** 面板声明从平铺的 `widgets` 换成 `rows`，
每行自己说是均布还是可变宽度；`orientation`、按钮的 `inline`、文本框的 `required`
三个字段删除，不留兼容分支。三个仓（Aurora 自持四页、Janus 四个面板、Mercury 两个面板）
的声明全部改写。

**为什么不做兼容分支。** 兼容意味着两套排版同时活着，而「这份声明按哪一套排」
会取决于有没有写某个字段——那正是这一版要消灭的东西。1.9.2 之前面板确实有两套：
竖排是三列共享的 Grid（行行对齐得像张表，不换行），横排是统一列宽的自动换行面
（所有元素被拉成同一个宽度）。两套都表达不了「这三个是一行、那一个自己一行」——
竖排里行是 `inline` 的副产品，横排里行是宽度算出来的结果。

**用户是在 Janus 的项目操作面板上撞到的。** 那三行本来就没有对齐的理由，
而对齐的代价是最长的那个按钮把另外两行的输入框一起挤窄。

**`required` 的账单独记。** 它的校验是全局的：面板上任何一个必填框为空，
**每个**按钮都拒绝执行，而报出来的错说的是那个框的名字，看上去与你点的按钮毫无关系。
Janus 的声明里有一段注释专门解释「因此不敢用它」；Mercury 三个数字框全写了它，
却共用同一批按钮，等于把整块面板锁在「三个都填了」上。
一个两个消费方都在绕开的字段不是能力，是陷阱。

**代价。** 九处声明重写，跨三个仓。这次接受，因为行的语义本来就该由声明给出——
在 `inline` 上继续叠字段只会让「第几行是什么样」永远说不清。

## DEC-019 缺的组件能力就补组件，不给某一页开后门

**2026-08-29（1.9.2）。** 选择框新增 `optionsSource`：候选来自一条只读指令，
参数里可以引用选择通道，通道一变就重取。命令集的域/类两级联动下拉据此恢复。

**它推翻的是 DEC-018 的一句副产品，不是 DEC-018 本身。** DEC-018 定的原则是
「页面适配组件、组件保持克制」，落地时净新增组件能力为 0，因此削掉了域/类联动下拉——
理由写在 `HostedPageData` 的注释里：「联动下拉的候选是动态的，而控制面板的选项框
只收静态候选」。

那句话当时是对的，但它记的是一笔**能力欠账**，不是一条永久结论。
DEC-018 真正的价值是「界面自己先撞上缺件」——现在界面撞上了，
正确的兑现方式是**补组件**，而不是继续绕开它、或者给命令集单开一条私有路径。
后者才是 DEC-005 要禁的东西。

**形状不新造。** `optionsSource` 与表格的 `dataSource` 是同一套：一条只读指令加固定参数，
返回行集，参数值里可以写 `{selection.<通道>.<列>}`。模块已经会写前者，
这里换个词只会多一份要各自维护的规则。

**它没有把面板变成脚本。** 面板只会「取一次候选」，不会按顺序做两件事，
也不决定拿到候选之后干什么——DEC-005 那条线一步没动。

## DEC-018 界面用自己的协议描述自己的页面，缺件由界面自己先撞上

**2026-08-27（1.9.0）。** Aurora 自持的四页全部改成页面描述，与模块页共用同一个
解析器、渲染器与包边。

**为什么。** 此前只有组件测试页是描述式的，命令集、指令详情、模块管理三页是手搓 WPF。
于是 DEC-005「模块不得自建组件」这条禁令，**界面自己是全仓最大的违反者**。

这不只是个观感问题。组件层缺什么，此前只有模块作者会撞上——而他们没有权限补，
只能提一张组件申请单等排期。界面自己不用这套协议，就永远不会先撞到墙，
于是「缺件」这件事在界面这一侧是完全不可见的。

改成自己消费自己之后，这条协议表达不了的东西就是组件层真正缺的东西，
**而且是界面自己先疼**。

**代价，逐条在案。** 本轮定的原则是「页面适配组件，组件保持克制」：凡是现有组件
表达不了的，削页面，不加组件。净新增组件能力为 0。因此删掉了域/类两级联动下拉、
命令集搜索框的补全、三页的状态行，行操作「复制指令名」改成「复制示例」。
逐条写在 REQ-UI-052 里，不假装没发生。

**顺带查出的事。** 逼界面自用之后当场撞出一条：`view.filterable` / `sortable` /
`selection` 在 schema 里声明、解析器里解析，**全仓没有一处读它**。这正是这套协议
要消灭的失败形态，只不过这次是协议自己犯的。记在 REQ-UI-054，本版不实现也不删。

关联：REQ-UI-052、REQ-UI-053、REQ-UI-054、DEC-005、DEC-017

## DEC-017 界面分三层，依赖只能向下，并且有门禁

**2026-08-27（1.9.0）。** 界面显式分成基础层（页面外壳：停靠、顶栏、拖出拖入、
页面合并、弹窗）、组件层（演进层：风格令牌、表格、控制面板、泳道、描述与渲染器）、
页面层（Aurora 自己托管的那几页），另加中立层与装配根，依赖只能向下。

**为什么现在做。** 逐目录比对 `using` 的结果是：**依赖方向已经是干净的单向**。
`Docking/` 不引用任何别的 Aurora 目录，`Views/` 一次都没碰过 `Docking/`。
三层早就存在，只是没被承认，也没有任何东西拦着它被破坏。

所以这条决定的实质不是「重构」，而是**把既成事实变成约束**。没有门禁的分层会在
第一次「就这一次」里破掉，而破掉的当天没有任何症状——等到基础层为了显示一个按钮
去 using 组件层，再想拆开就已经晚了。

**最容易破的那一条写死在合同里**：顶栏上的页面动作必须由组件层翻译成纯数据清单
交给基础层，基础层不得反过来去问组件。它听起来像是顶栏的事，所以一定会有人这么写。

**这一版不动目录。** 命名空间与文件夹保持原样，分层靠合同与门禁表达。物理重排留给
以后单独一版——`ModulesView.xaml` 一类的 pack URI 按短名解析主题字典，搬 `Themes/`
会打断它，那件事不该和本轮混在一起。

关联：REQ-UI-049、DEC-014、DEC-018

## DEC-012 按钮绑动作 id，不绑指令名

- 状态：已接受
- 日期：2026-08-24
- 裁决原文：「按钮绑定的方法必须由其他模块声明获得（防止改指令导致按钮失效的问题）。」
- 决策：四条——
  1. 面板按钮**只接受动作 id**，写指令名即校验失败；
  2. 动作由模块经 `<域>.ui.actions` 自行声明，指令名归声明管，Aurora 主动拉取；
  3. 动作解析不到时按钮**不渲染成按钮**，而是一块写着原因的警示牌；
  4. 声明指向不存在的指令进"断链"账，`aurora.ui.actions` 可查。
- 原因：旧的面板按钮直接写指令模板。模块改一次指令名，所有写死该名字的按钮同时变哑——
  点了没反应、没有报错、也没有任何地方记下这件事。这类缺陷的成本不在修，在于**发现**：
  它只在有人恰好点到那个按钮、且恰好记得它以前能用的时候才暴露。
- 为什么不改成"启动时校验指令是否存在，不存在就禁用按钮"：那只是把静默失败换了个样子。
  禁用按钮看起来像"当前不可用"，与"这个按钮已经彻底断了"无从区分。
  真正的修法是让**按钮不再记住指令名**。
- 已知代价（明确接受）：模块必须多注册一条 `.ui.actions`。这是刻意的——
  动作是模块对外的承诺，承诺就该写在模块自己那里，而不是散落在各处的面板 JSON 里。
- 与 DEC-005 的关系：同一条思路的两次应用。DEC-005 让模块不再持有**样式**，
  本条让面板不再持有**指令名**——两次都是把易变的东西收回它的所有者手里。
- 替代条件：只有证明"指令名足够稳定，改名可以被其它机制全量发现"的同级决策可以替代。

## DEC-008 界面回归模块形态，独立 exe 退役

- 状态：已接受
- 日期：2026-08-20
- 裁决原文：「如果有 exe 文件的话，别单独发，我们从逻辑上也把他视为一个模块。启动什么的

- 决策：四条——
  1. Aurora **没有独立 exe**。界面是宿主装载的一个模块，在宿主进程内开窗；
  2. 启动与显隐一律走注册的指令，不再有第二个可执行文件暴露给用户；
  3. 发布只有**一个包**，就是模块包；
  4. 桌面快捷入口归 Mercury 活动坞，它调指令而不是指路径。
- 与 DEC-004 的关系：**推翻其第 1、2 条**。DEC-004 判「模块路径到不了那个进程」，
  证据采自**双角色 exe 时代**——那时模块命令落在服务进程、界面在另一个进程。
  4.0.0 之后只剩一个进程，那条推理的前提已不存在。
  DEC-004 的第 3 条（自持命令注册表）与第 4 条（Core 解冻）继续有效。
- 支持这次改判的实测：`Shell` 的 10,678 行几乎不依赖 `Application`——全仓仅一处
  `Application.Current` 且**本就空值守卫**，`App.xaml` 一个字典都没合并，
  主题全挂在 `ShellWindow.Resources` / `DockManager.Resources` / 浮动窗口上。
  界面代码早就是窗口作用域的，`Application` 实例接近摆设。

### 施工中撞到的四个障碍，以及后来怎么热重载

**一、可回收上下文 + WPF 不能「先装新再卸旧」。** 冷启动仍会重载 2–3 次。旧实现用
`pinned: true` 把 Aurora 钉进 `AssemblyLoadContext.Default`：不卸载、静态字段跨重载存活、
`EnsureStarted` 做幂等。代价是更新界面必须重启宿主，DLL 也被 Default 锁死。
现行做法：manifest **不再 pinned**。宿主整体 Reload **先 DestroyUi 并卸载旧可回收 ALC，再 Build**。
Aurora 的 `DestroyUi` 关掉窗口、停 Dispatcher、Join STA 线程。冷启动多轮重载会闪一下窗口，
这是可接受的；未改包 SHA 时复用 ALC 是后续优化，不是本轮范围。

**二、XAML 按程序集简单名走默认上下文。** 第一次实现用不可回收自定义 ALC，
`ShellWindow.InitializeComponent()` 在 `ResourceDictionary.DeferrableContent` 上抛
`XamlParseException：类型引用无法找到 {…;assembly=AvalonDock.Themes.VS2013}`。
钉住路径的补丁是 `LoadFromAssemblyPath` 进 Default——那正是卸不掉的原因。
现行热重载路径：默认上下文的 `Resolving` **只返回**可回收 ALC 里已经装好的程序集，
绝不把它们装进 Default。`pinned: true` 仍保留给真正不能拆的模块。
残余风险：WPF 的 `PropertyMetadata`、pack URI 表、未完成的 Dispatcher 操作可能继续
抓住 Type，使旧 ALC 实际卸不干净。那是泄漏，不是第二扇窗——只要旧 Resolving 已摘掉，
新解析只看当前 ALC 集合。

**三、宿主进程要拿到 WPF 运行时。** WPF 是共享框架，模块自带不了；宿主 `runtimeconfig`
里没有 `Microsoft.WindowsDesktop.App` 就直接 `FileNotFoundException`。
宿主 App 工程因此加了 `<FrameworkReference Include="Microsoft.WindowsDesktop.App.WPF" />`——
**只加框架引用，不开 `UseWPF`**：宿主工程仍然零界面代码、零 XAML 编译、没有 App.xaml，
REQ-A8「宿主不引用 WPF」在源码层面继续成立。变的是运行时前提：
**本进程从此要求机器装有 WindowsDesktop 运行时**。这是"界面住进宿主"的必要代价。

**四、宿主的模块 UI 生命周期跑在非 STA 线程上。** 模块一建控件就抛"调用线程必须为 STA"，
而该异常被按模块吞掉——表现为某个模块的页面悄悄少一个，别的模块照常，日志里只有一条 Warn。
`ModuleHost.CreateUi` 经 `IShellUiRegistrar.Invoke` 编组到界面线程。
`IShellUiProvider.DestroyUi` **不得**再走 `Invoke`：提供方要在服务线程上 Join 自己的 STA 线程。
其它 UI 模块仍 `Invoke`，且必须在提供方关机之前拆完。

### 新增的宿主契约

`IShellUiProvider`：由模块**反向提供**界面注册器。与 `IShellUiAware` 方向相反——
界面整体成为模块之后，宿主自己不再持有任何界面实现，注册器只能来自模块。
宿主在 `CreateUi` 阶段先取遍提供方再分发给消费方：模块装载顺序不可控，
靠目录名排序碰巧让提供方排在前面是不能依赖的。

`ServiceComposer` 的 `EnableUiModules` 由 false 改为 true。这不会让宿主长出界面：
没有模块实现 `IShellUiProvider` 时 `ShellUi` 保持 null，`CreateUi` 整段跳过，
进程仍是纯无头的。

### 验收（2026-08-20 真机实测）

宿主进程内 `aurora.ui.windows` 返回 7 个窗口：console / modules（框架）、
overview / graph / projops（Janus）、dock.manager（Mercury）、historyminerva（Minerva）。
域分布 aurora 40 / diana 29 / janus 36 / mercury 26 / minerva 9 / vulcan 32。
进程列表里**只有 HistoryVulcan.exe 一个**。

### 未尽项

- `vulcan.app.show` 等冷启动路径仍指向宿主自身可执行文件（4.0.0 起等同再起一个无头服务）。
  界面进程内之后这条应改为"叫醒本进程内的窗口"，尚未改。
- Mercury 的管理页注册在 `StaticResourceExtension` 上报过一次警告，待逐页复核。
- 宿主快照（`z-Publish/host`）尚未刷新，Aurora 目前靠 `Directory.Build.user.props`
  指向未发布的宿主构建输出联调。

- 替代条件：只有证明"界面必须与服务分属两个进程"的同级决策可以替代。

## DEC-007 Aurora 登记进 Vulcan 注册表，不因是应用而免登记

- 状态：已接受
- 日期：2026-08-20
- 裁决原文：「模块注册应该指的是注册在 vulcan 里面的，aurora 既然是前端就模块应该注册在
  vulcan 里面而不算宿主，否则特殊模块太多了；页面注册应该走的是模块间调用而不算模块
  寄生在宿主内」。
- 决策：三条——
  1. Aurora 在 Vulcan 的模块注册表里**有平级身份**，在「模块管理」中与 Diana / Janus /
     Mercury / Minerva 并列显示，不因为它恰好是承载模块的那个进程而免于登记；
  2. 宿主之所以是宿主，只因为它持有指令总线与注册表本身。**前端不属于宿主**；
  3. 页面注册的目标形态是**模块间调用**（模块调 Aurora 的页面契约），而不是模块经宿主的
     模块契约声明窗口。
- 与 DEC-004 的关系：**不冲突，各管一段**。DEC-004 管的是命令投递路径——实测证明前端命令
  无法经「装载进服务进程的模块」投递（`DataDirectory` 会变、够不到 `ShellWindow` 与 UI 线程），
  该结论继续成立。DEC-007 管的是注册表身份。二者同时为真：Aurora 是应用进程，
  同时在注册表里是一个 `MainClassType = null` 的模块条目。
- 为什么不按进程边界发特例：特例会累积。「承载模块的进程不登记」这条规则一旦成立，
  下一个同时是应用又是模块的东西就要再判一次，而判据（谁装载谁）与注册表要回答的问题
  （体系里有哪些部件）无关。
- 实施发现：Aurora 仓的 Module 工程**从来没有 `ModuleInfoBase` 子类**，因此它编出的 DLL
  根本不会被宿主识别为模块（宿主按基类全名 `BaseVariable.ModuleInfoBase` 做鸭子类型识别，
  MD-02），只会被当成普通依赖库。此前能出现在模块管理里的 `HistoryAurora 0.2.0` 是一个
  **孤儿二进制**——它有 `ModuleInfo` 与 `Commands.ConsoleCommandGroup`，
  但 `git log --all -S` 在本仓搜不到任何一处对应源码。
- 施工约束（两条互相牵制，缺一即错）：
  1. 模块程序集名必须是 `HistoryAurora.Module` 而非 `HistoryAurora`。与 App 同名会在同进程内
     遮蔽 pack URI 的资源解析——WPF 按程序集**短名**解析 `/HistoryAurora;component/…`，
     App 有 `.g.resources` 而模块没有，先命中模块就找不到主题。实测表现为 AvalonDock 抛
     `IOException 找不到资源 themes/auroratheme.baml`，主界面停靠浮动层失效，且编译期零征兆。
  2. 因此 `ModuleInfo.ModuleName` 必须**显式覆写**回 `HistoryAurora`。基类默认取程序集名，
     而 ModuleName 同时就是指令域名；不覆写会让域从 `aurora` 漂成别的值。
- 未尽项：页面注册仍是「模块经宿主声明窗口」的旧形态（日志可见 `模块 X 的窗口 Y 声明中央区`）。
  改为模块间调用需要先有 Aurora 侧的页面描述契约，属于 C 阶段，本轮未动。
- 替代条件：只有证明「承载模块的进程不能同时是注册表条目」的同级决策可以替代。

## DEC-005 组件键名整体改为 `Aurora.*`，模块不得自建组件

- 状态：已接受
- 日期：2026-08-19
- 决策：借前端切出这次机会做**一次性破坏性重构**，三条同时生效：
  1. 全部设计令牌与具名样式从 `Shell.*` 改为 `Aurora.*`（65 个令牌 + 16 个样式）；
  2. **不提供 `Shell.*` 别名、不设弃用期、不做双键并存**；
  3. 模块 XAML **不得出现 `Style x:Key=` 与 `<ControlTemplate>`**，界面一律走组件库。
- 为什么不保留别名：别名本身就是技术债。双键并存意味着每个组件维护两套键、每次演进同步
  两处，且无法判断某个模块实际用的是哪一套；而"弃用期"在实践中等于永久保留——三个模块
  各按自己的节奏适配，没有任何力量会促成最后一次删除。一次性断掉，反而让适配成为一件
  有明确完成标志的事。
- 为什么禁止模块自建组件：实测三个模块共自造 2 个具名样式 + 4 个 ControlTemplate，
  且全部源于同一个原因——分段家族缺 Toggle 成员（见
  [前端组件计划表V1.0](../history/前端组件计划表V1.0.md)）。自造版本不跟随主题演进，
  最终表现为"只有这一页长得不一样"。禁止自造的前提是**组件库先补齐**，
  因此 `Aurora.Segment.Toggle` 是解禁的前置条件，不是可选项。
- 已知代价（明确接受）：`DynamicResource` 找不到键时 WPF **不抛异常**，只是不套用该值。
  模块在适配前不会崩，而是**静默退化成 WPF 默认外观**。静默失败比硬失败难发现，
  因此必须配一个可执行检查器（见 REQ-UI-002），让"哪些模块尚未适配"成为可查询的事实，
  而不是靠肉眼看出哪一页变丑。
- 兼容立场：模块在切出完成后反过来做适配更新；本仓不为此排期、不保留过渡机制。
- 替代条件：只有证明"键名必须与提供方产品名解耦"的同级决策可以替代。
