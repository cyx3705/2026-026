# HistoryAurora 技术合同

## 表格加载与统一表头（1.20.4，REQ-UI-108 ～ 110）

- REQ-UI-108：表头整行复用 `Aurora.Panel.Surface` 的底色、圆角和 Padding，内部高取
  `Aurora.Size.Control`；隐藏 GridView Padding 表头，删除行容器左右额外内距，剩余列宽归最右数据列。
  垂直滚动条仍保留其必要视口宽度。取代 REQ-UI-039 对表头占位和行左右内距的旧说明。
- REQ-UI-109：显式启用虚拟化、回收和像素滚动；列声明未变不重建列，相同行不通知；
  取数与 JSON 解析放后台，控件更新回 Dispatcher；同表一次最多一个请求，期间重复刷新合并为一次补取，
  过期结果丢弃。`dataSource.rowKey/deltaCommand` 接入版本增量协议，旧行数组兼容。
  `AuroraTable.ApplyDelta(rowKey, upserts, removes)` 合并字段、追加新行、删除旧行，非法批次原子拒绝。
  未修改行保留对象，选择通知在批次完成后最多一次；有 rowKey 的快照按键恢复选择。
- REQ-UI-110：刷新中保留上次表格；常驻状态栏显示加载/刷新/失败、当前数量、最后成功更新时间。
  失败不清空、不推进 revision；选择参数未就绪时清空并说明等待原因，避免误操作其它项目数据。
  不做磁盘数据缓存。模块自身首次扫描耗时不在 Aurora 内虚构提速，消费方接增量后才能减少业务扫描。

验收：`TableUpdateContractTests`、表头/比例/列宽及选择通道合同测试。万行仅创建有界可见行容器；
连续 20 次刷新合并；revision 传递、失败保留、无效批次拒绝均经执行路径验证。


本文件记录现行要求。每项要求有编号、目的、可验证的要求条目和验收方式。

当前源码为 **1.20.3**。消费的宿主版本由 `b-Code-Studio/AuroraVersion.props` 的
`MinimumHistoryVulcanVersion` 单点声明，当前为 **5.1.0**。

1.17.0 新增的 `aurora.host.ready` 不抬这条下限：它没有用到任何新的宿主公开面，
在 5.1.2 及以前只是注册表里一条永远不会被调用的命令（见 REQ-UI-075）。

### REQ-UI-103 顶栏残留清理与停靠层扁平化（1.20.3）

- 目的：1.20.2 删的是顶栏这个**东西**，留下的是围着它长出来的壳——没人画的页签模板、没人读的字段、
  为「一格多页」分出来的文件切分。壳留着不报错，只是让下一个人以为它们还有用。
- 要求：
  1. **页签视觉清零**：`Aurora.Docking.TabItemTemplate` 只剩一块透明 `Border`；标题文字、关闭按钮、
     悬停与选中触发器（约 90 行）删除。页签容器（`ItemContainerStyle` → `LayoutXxxTabItem`）**保留**——
     窗格控件是 `TabControl`，要靠生成出来的容器才产出 `SelectedContent`（REQ-UI-101 第 1 条）。
  2. **死代码删除**：`DelayedDragGesture`（1.20.2 删掉 0.3 秒延迟后无人调用，只剩 5 条测试供着它）、
     `DockingDragSession.Target` / `RequiresHold`（写进去从没被读过）、`ShellWindow.Chrome.cs` 里只被
     自己递归调用的 `FindDescendants<T>`、令牌 `Aurora.Space.TabStrip`（全仓无引用）。
  3. **停靠层收成三个文件**，各答一个问题：`DockingHost.cs` 对外是什么（生命周期、`IDockingService`、
     布局差分、状态与查找）、`DockingHost.Layout.cs` 布局树怎么摆（默认布局、放置、一格一页、比例、中央区修复）、
     `DockingHost.Snapshot.cs` 怎么存怎么取（快照序列化与恢复、场景切换）。
     `ISceneDocking` 搬进 `DockingContracts.cs`，与 `IDockingService` 并列。
  4. **快照尺寸四项统一走反射**：`ApplyPosition` / `TryGetPosition` 原本是五路 switch 加五个同名同体的
     `Set` 重载，一百多行里没有一行是各自不同的判断；本类的 `GetDockLength` / `SetDockLength` 早就用反射
     绕过同一个 internal 接口。`RestoreContent` 的 `documentPane` 形参删除（1.20.2 起就没人读）。
  5. 行为不变：本条不改任何用户可见的行为，判据是 1.20.2 的全部用例原样通过。
- 验收：见验证合同 1.20.3。

### REQ-UI-104 右栏与停靠区是同一片画布（1.20.3）

### REQ-UI-105 Ctrl 标签态保持卡片圆角（1.20.3）

- 目的：用户原话「按住 CTRL 的时候……组件页的边缘变成了尖角矩形而不是圆角矩形」。

- 验收：`ShellChromeContractTests.LabelModeCoverKeepsTheCardCorners`。

### REQ-UI-106 搜索并进右栏，浮层退役（1.20.3）

- 目的：用户原话「搜索不需要弹出独立页面，而是直接在右侧场景控制栏上搜，同时支持页面和场景的搜索，
  下面的场景和页面会随着搜索筛选为候选项」。
- 要求：
  1. 搜索框是右栏第二行（与错误徽章同一行）。输入随手**筛下面那两段**：上半的场景、下半的常用页面。
  2. 搜索浮层 `NavOverlay`（底板、卡片、结果列表与派生索引）整体删除。
  3. **动作不再进搜索**（用户拍板）：动作条目从来只是「切到它所在模块的场景」，与直接搜场景重合。
  4. 检索文本只用已声明的字段（标题、id、owner），每个词都得命中；标题开头 > 包含；再按使用频次加权。
  5. 回车打开排在最前的候选：有场景候选就切场景（`aurora.scene.go`），否则开页（`aurora.scene.open`）。
     **胶囊的点击语义不变**（用户拍板）：点一下什么都不做，只能拖——不推翻 DEC-034 决策 5。
  6. `aurora.nav.open` 保留，落点从「开浮层」换成「把窗口请到前台并聚焦右栏搜索框」；
     Mercury 注册的全局快捷键（默认 `Ctrl+Alt+K`）照旧。
  7. 页面候选取的是**此刻没露面的页**——右栏下半本来就是这份清单（REQ-UI-099），搜索也在它里面搜。
     已经露面的页不进候选，它就在屏幕上。
- 验收：`ShellChromeContractTests.RailSearchFiltersScenesAndPagesWithoutAnOverlay`。

### REQ-UI-107 拖动面覆盖右栏与停靠区画布（1.20.3）

- 目的：用户原话「拖动整体现在只有一小部分区域可以拖，请让拖动可以直接覆盖整个场景控制栏和页面底部的融合区」。
- 要求：
  1. 右栏**整条**的空白处都能拖窗口、双击最大化，包括两段滚动区里的空处。
  2. 停靠区里卡片之外的画布同样可拖——判据是命中的就是 `DockingManager` 自己：窗格、分隔条、
     自动隐藏边条都有自己的命中面，页面内容再怎么点也走不到这里。
  3. 按钮、搜索框、滚动条与常用页面胶囊仍归它们自己，胶囊的拖动会话不被窗口拖动抢走。
  4. 最大化时不拖（`DragMove` 在最大化下会抛），双击还原照常。
- 为什么改走 Preview：原先挂在冒泡的 `MouseLeftButtonDown` 上，右栏里占了两整行的滚动区先把按下吃掉，
  冒泡上来时能拖的只剩边角那几条缝——用户报的「只有一小部分区域可以拖」就是这个。
- 说明：卡片外缘间隙 `Aurora.Space.Gap` 只有 1，停靠区可拖的画布因此很窄；这一条的主体是右栏。
- 验收：`ShellChromeContractTests.RailBlankSpaceIsAWindowDragSurface`。

## 一格一页改为结构性约束、顶栏删除（1.20.2，REQ-UI-100 改写、REQ-UI-101 / 102）

> 决策见 DEC-034。用户真机试 1.20.1：一个位置会在几个曾经拖入过的页面之间**循环抢占**——
> 说明一格里仍允许多页存在，只是只显示一页。本版把「一格多页 + 挑一页留下」整条链删掉，并删除顶栏。

### REQ-UI-100 一格一页（1.20.2 改写）

- 要求：
  1. 主文档区、侧边与底边窗格、浮窗里的窗格，**任何时刻只放一页**。程序路径（`Show` / `Dock` / `ResetWindow` /
     场景 / 登记 / 恢复）放一页进一格，**先把这一格原来那一页隐藏，再放进去**，不存在「先挤进去再挑」。
  2. 不抢位的放法（登记、恢复布局、补齐快照里没有的页、拖出落空摆回默认位置）：这一格已经有页，新来的直接隐藏。
     **没有等位**：不记账，占位页后来被隐藏也没有别的页自己补进来；要它露面走右栏胶囊或 `aurora.ui.show`。
  3. 唯一绕不开的入口是 AvalonDock 的「放进这一格」停靠点（它把拖来的页插成第二页）：布局一变就收拾，
     留刚从浮窗落下来的那一页，其次活动页、选中页。1.20.1 及以前存下的多页格子，启动、恢复、切场景时每格留选中页。
  4. 没有标签组：`aurora.ui.dock` 不再接受 `pos=tab`；页面声明里的 `side=tab tabTarget=X`（Janus 的「图」）
     只表示「与 X 同一个位置」——X 此刻在哪一格就进哪一格（不抢位）；X 藏着（常见的是刚被顶掉）就按 X 上次露面的方位；
     X 从没露过面（还没登记）才按 X 的默认方位。跟随页先于目标登记时按兜底方位放，之后不再追着目标挪位。
  5. 场景按初值定显隐：初值里的页只在位置空着时露面；模块场景里本模块的页最后露面并顶掉它位置上的页
     （Janus 场景露「图」、控制台藏着）。当前场景里新登记的页：外来页先被场景藏掉，本场景的页再按初值看一次位置，
     空着就露面——只在登记那一刻看一次，不是等位。
- 删除的实现：等位账 `_waitingForSeat`、「每页在哪一格」历史 `_pagePanes`、`newcomersWin` / `prefer` 挑选、
  延迟标签组目标 `_pendingTabTargets`、侧栏标签组合并 `ConsolidateSidePanes`、位置台账里的标签组目标与中央区下标
  （字段保留以读旧台账，写入一律为空）。
- 验收：见验证合同 1.20.2。

### REQ-UI-101 顶栏删除（1.20.2）

- 要求：
  1. 所有窗格模板不再画页签行（常规态、专注态、浮窗同一套）。页签面板仍保留在高 0、不可见、不接收输入的一行里——
     窗格控件是 `TabControl`，要靠生成出来的页签容器才产出 `SelectedContent`，整个拿掉内容区就是空白。
  2. 随顶栏一起删除：双击页签专注、按页签换页、页签拖动、AvalonDock 原生页签拖动的卸膛（`NativeTabDrag`）、
     页头拖动主窗口与浮窗、窗口控制组的第二个落点（主文档区页头、专注页页头）、页签行占位、
     工具页头的「恢复页面」、浮窗页头的最大化按钮、`Aurora.Command.PageAction`、配置项 `EnableMaximizeOnDoubleClick`。
  3. 窗口控制组只在右栏顶部，专注态右栏也不让位；拖动主窗口走右栏空白处。退出专注：右栏按钮、F11、Esc。
  4. 页面拖动只剩两条来路：Ctrl 标签态、右栏胶囊。拖动协调器由 `ShellTopBarCoordinator` 更名为 `PageDragCoordinator`；
     单页浮窗靠标签态拖标签移动。
  5. 右栏胶囊**只用来拖**：点一下什么都不做（1.20.1 点一下会打开页面，用户真机当成 bug）。
- 验收：见验证合同 1.20.2。

### REQ-UI-100 每一格只留一页（1.20.1，推广 REQ-UI-096）

- 要求：
  1. 主文档区、侧边与底边窗格、浮窗里的窗格，**每一格**一旦出现第二页，只留最后进来的那一页，其余隐藏。
     自动隐藏的边条不算格子。
  2. 留哪一页，依次：调用方点名的（`Show` / `Dock` / `ResetWindow`）→ 场景传来的本模块页 →
     用户拖进来的（比对上一次记下的「每页在哪一格」）→ 选中页 → 最后一页。
     登记、恢复布局、切场景不抢位：留原来就在那一格的页。
  3. `aurora.ui.dock pos=tab target=X` 并进 X 那一格即顶掉 X——并标签组从此等于「换这一格的页」。
  4. 等位：新登记的页落进有页的一格而被藏，占位的页随后被**明确隐藏**时（`aurora.ui.hide`、场景藏外来页），
     它回到这个位子。只等一次；切场景、换布局即清空，不会在别的场景里冒出来。
     没有这一条，同一批热重载里先占位的外来页被场景藏掉后，那一格空着、本场景的新页也不露面。
  5. 模块场景里本模块的页优先于常驻页：Janus 的「图」并在控制台那一格，进 Janus 露「图」、控制台藏着；
     在别的场景仍是控制台。
  6. 1.20.0 及以前存下的多页格子（含 Janus「图」+ 控制台的标签组），启动与恢复时每格只留选中的那一页。
- 验收：`DockingContractTests.EveryPaneKeepsOnlyTheLastPageIn`（含「非中央页拖进主文档区」「拖进底边格」两段用户拖放）、
  `PageRegisteredIntoAnOccupiedPaneTakesTheSeatWhenItFreesUp`；按新规矩改写的 12 条旧用例
  （标签组、台账回退、快照恢复、延迟登记、场景首访与等位）。

## 顶栏退役第一步（1.20.0，REQ-UI-094 ～ 099）

> 决策见 DEC-032。顶栏最终要整个删掉；本版**先转移、不删除**顶栏本身，只删掉工具页右侧的 ▼ 菜单与 ✕。
> 本版改写了 REQ-UI-084 / 085 / 088 / 089 的部分条目、作废 REQ-UI-087，改动处都在原条目里注明。

### REQ-UI-094 场景只是一份布局，不拥有页面（1.20.0，破坏性）

- 目的：场景之间的区别只是页面的显示与隐藏（用户原话：「场景本身只显示和隐藏页面而已」）。
- 要求：
  1. 场景 = 以场景 id 命名的命名布局。页面集合、增补、剔除与断链账整套删除，`SceneInfo` 不再有页数与断链。
  2. `aurora.scene.add / remove` 退役，显隐就是 `aurora.ui.show / hide`。
     `aurora.scene.open` 改为在当前场景里打开，不再切到「含它的场景」。
  3. 初值规则：场景没有布局可恢复时（第一次进入、重置），「全部」露出每一页，模块场景露出该模块的页与常驻页，
     另存场景露出此刻露面的页。之后完全按离开时的样子恢复；布局存下之后才登记的页按初值规则定显隐。
  4. 另存场景没有初值可回，只能在它是当前场景时重置。

## REQ-UI-083 中央文档区必须认得工具页的下标（1.18.4）

> 本条结清 REQ-UI-082 的挂账「中央页全是 anchorable 带来的模型选中失效」，
> 并修掉由它派生的真机症状：中央页拖不动。**REQ-UI-082 不被推翻**——
> 页签左键仍然整个交给 AvalonDock，本条一个手势都不拦。

- 目的：中央区里两种身份的页签行为一致：点得动、拖得动。
- 背景：中央区是一排页签，混着两种身份——命令集是 `LayoutDocument`，
  其余中央页（模块页与 Aurora 自持的几页）是 `LayoutAnchorable`。
  `LayoutDocumentPane` 的 `ILayoutContentSelector.IndexOf` **只认前者**，
  对 anchorable 一律返回 -1。这一个 -1 扩散成两个用户可见的故障：
  1. **换不了页**：`LayoutContent.IsSelected` 的 setter 回写
     `Parent.SelectedContentIndex = Parent.IndexOf(this)`，写进去的是 -1，
     窗格于是什么都不选——页签照画、内容空白，而 `aurora.ui.show` 还报成功；
  2. **拖不动**：AvalonDock 自己那条页签拖拽按同一个下标记住来处
     （`PreviousContainerIndex`），-1 让整条拖拽起不来。
     真机症状是「Janus 的项目总览拖不动，旁边的命令集拖得动」（2026-09-07）。
- 要求：
  1. Aurora 建的每一个中央文档窗格都是 `CenterDocumentPane`——
     它派生自 `LayoutDocumentPane` 并**重新实现 `ILayoutContentSelector`**，
     `IndexOf` 走 `Children.IndexOf`。接口映射指向派生类，
     于是换页、拖动、快照恢复三条路径同时正确。
  2. 两处建窗格的地方都必须用它：默认布局与快照恢复。
  3. **AvalonDock 自己建的那种要在布局差分里换掉**（`UpgradeStockDocumentPanes`）。
     把一页浮出去再丢回中央区、或者把中央区拖成两半，新窗格是原装的
     `LayoutDocumentPane`——故障会在那一格里当场复发，而且只在拖过的那台机器上复发。
     换的时候连孩子、尺寸与选中页一起搬：选中页先看窗格，窗格已被 -1 写坏时
     退回去问内容自己的 `IsSelected`。
  4. **窗格控件要跟上模型的选中页**（`SyncPaneControlSelection`）。
     模型改对不等于屏幕换页：换页那一跳会先经过一个 -1，`TabControl` 在那一下之后
     可能不跟了——真机症状是 `aurora.ui.show` 报成功、布局快照里 `selectedContentId`
     也对，而屏幕仍停在原来那一页。因此在同一轮呈现里按模型对齐一次控件；
     两边一致时不动，不打断用户自己点出来的选中。
  5. **不在手势层拦截**。1.17.2 与 1.17.5 各试过一次「Aurora 接管页签左键」，
     两次都把换页弄坏（REQ-UI-082 已推翻那条路线）；本轮 1.18.1 又试了一次
     「只接管工具身份那一半」，同样弄坏——下标才是病根，手势不是。
  6. **注册协议给不出主页面**：文档身份只由 `IsPrimaryCommandDocument` 决定，
     模块声明 `side=center` 拿到的一直是工具窗口。这不是本轮新增的行为，
     而是把一条一直成立、却没人守着的约束钉进门禁
     （`DockingContractTests.RegistrationNeverProducesASecondMainDocument`）。

## REQ-UI-039 表格按页面宽度等比缩放（1.8.15）

- 目的：表格永远铺满可用宽度，右边不留空扩展区，也不长横向滚动条。

## REQ-UI-041 选择通道：表格与控制面板的跨页面接线（1.8.16）

- 目的：把 1.8.14 随页面按钮一同退役的「表格选中行 → 按钮变可用」接回来，
  并且**跨页面**可用。
- 背景：1.8.14 收敛页面节点时，页面按钮的 `invoke` / `enabledWhen` 与 `input.suggest`
  一起退役（REQ-UI-038），能力损失是明写在案的。真正卡住使用方的是第二件事——
  Janus 的项目表在中央的「项目总览」页、操作面板在左侧的「项目操作」页，
  就算 `enabledWhen` 还在，它的落点是**页内节点 id**，而页面是一页一页渲染的
  （`PageRenderer.RenderState` 的节点表作用域就是一页），跨不过页边界。
- 要求（通道是界面级的）：表格用 `channel` 声明把当前选中行发布到一个具名通道；
  台账 `SelectionChannels` 由 `ShellWindow` 单点持有，因此天然跨页。
- 要求（三个落点）：面板文本框 `follows: "<通道>.<列>"` 跟随取值；
  面板按钮 `enabledWhen: { "selected": "<通道>" }` 按有无选中启停；
  动作参数占位符 `{selection.<通道>.<列>}` 取选中行的值。
- 约束（两个命名空间必须分得开）：`{selection.*}` 走通道，其余仍按控件 id 走面板。
  改名这类动作要同时知道「改谁」和「改成什么」——跟随框里的值一旦被人改过就不再等于
  选中行，两者必须分别取得到，否则改名只能改成它自己。
- 约束（按最后一个点分）：通道名自己带点（`janus.project`）。按第一个点分会把
  `janus.project.name` 读成通道 `janus` 加列 `project.name`，而那个通道确实可能存在——
  错得毫无声响。列名不含点，最后一个点因此是确定的分界。
- 约束（同名通道只认第一个声明方）：后到的覆盖会让「按钮跟着哪张表走」取决于建页顺序，
  而建页顺序不受任何东西保证。与动作 id 撞名同一条线。
- 约束（通道是派生状态）：`ModulePageLoader.Drop` 撤页时按 owner 一并撤通道。

  正是宿主侧 `web.frontendcatalog` 的老毛病。
- 要求（断链必须出账）：引用了没人声明的通道，界面表现与「还没选中」完全一样。
  因此整轮建页之后统一判一次，记 Warn 并进 `aurora.ui.channels`。
  **不得在渲染期判**：面板所在的页可能先于表格所在的页渲染，那样会把正常情况报成断链。
- 附带修复（本轮实测撞出来的既有缺陷）：动作占位符的正则原本是 `\w+`，
  而 `\w` 不含连字符。`{project-name}` / `{commit-message}` / `{page-option}` 这类
  控件 id 因此**根本不被识别为占位符**——既不替换，也不算「引用了不存在的控件」，
  原样上了总线，成为一条参数明显错误却「执行成功」的指令。改为 `[^{}\s]+`。
- 验收：`SelectionChannelContractTests` 四条（跨页驱动、两个命名空间分得开、
  重名出声拒绝、断链出账）与
  `ActionDeclarationContractTests.BuildCommandText_AcceptsHyphenatedAndDottedPlaceholderNames`。
- 关联组件：`b-Code-Studio/Shell/2-Components/Selection/SelectionChannels.cs`、

## REQ-UI-044 取数可重来：跟着选中走，也能被显式刷新（1.8.16）

- 目的：表格与泳道图的数据不再是"建页那一刻的快照"。
- 背景（Janus 实测的两处）：
  - 取数只在控件 `Loaded` 时跑一次，此后没有任何再取的入口。
    「刷新」按钮因此只能把业务指令打到控制台，界面上那张表一动不动——
    **点了有反应，但没有用**。
  - 依赖当前选中项目的表（分支历史、规则落地状态）换一次选中就成了过期数据，
    而过期数据与新数据在界面上长得一模一样。图谱更直接：它固定画项目清单的第一条。
- 要求（取数参数可引用选中行）：`dataSource.args` 的值里可以写
  `{selection.<通道>.<列>}`，取数时用当前选中行替换（REQ-UI-041 的同一套引用）。
- 要求（引用的通道一变就重取）：`PageDataRefresher` 订阅通道变化，按绑定上记着的通道名分派。
  **只订阅一次**，按条目分派：每个绑定各订一次的话，撤页时漏解一个就留下一个
  指着废弃控件、还在发指令的处理器。
- 要求（取不到值就不发指令）：占位符解析不出来时**不执行**，表格显示空态并写明
  「请先选中一行」。没选中项目就去问「这个项目的历史」，拿回来的要么是错误、
  要么是别人的历史——两种都比一张写明原因的空表糟。
- 要求（跟随选中的重取要消抖）：连续的通道变化合并成最后一次，窗口 250ms。
  一次选中变化会触发这一页上全部引用该通道的取数（Janus 上是三条，其中落地状态
  每次跑两条 `git ls-files`）。
  **实测口径要说准**：键盘翻项目时选中变化间隔约 450~600ms、每条取数 120~220ms 返回，
  这个速度下是跟得上的，**没有观察到堆积**。消抖是防御——按住方向键或程序重设选中时
  间隔会短得多。250ms 小于实测的键盘间隔，因此正常翻页手感不变。
- 约束（显式刷新**不**消抖）：那是人按下按钮的那一刻，延迟 250ms 才动会被感知成卡了一下。
- 要求（显式刷新）：`aurora.ui.refreshdata [page=] [node=]`。回执必须把
  「刷了 N 处」与「一处都没匹配上」分开说：按钮点了没反应时，差别就在这一句上。
- 约束（绑定是派生状态）：`ModulePageLoader.Drop` 撤页时按 owner 一并撤绑定，
  与选择通道同一条理由——留着就是对着废弃控件继续发指令。
- 验收：`SelectionChannelContractTests` 三条——换选中会重取、按页/按节点分派且不误伤别页、
  撤 owner 连带撤绑定。
- 关联组件：`b-Code-Studio/Shell/2-Components/Pages/PageDataRefresher.cs`、
  `b-Code-Studio/Shell/2-Components/Pages/PageRenderer.cs`、`b-Code-Studio/Shell/4-Composition/BuiltinCommands.Channels.cs`
- 关联验证：`VERIFY-DATA-REFRESH`

## REQ-UI-046 页面切换容器：一块版面上轮换一批组件（1.8.17）

- 目的：把"三个页签"收成"一页里的一个控件"。停靠层能把三页并成标签组，

- 约束（`IsGreedy` 必须算上 switch）：分支里放着表格时少算的话，切过去看到的是

- 验收：`PageSwitchContractTests` 五条。

## REQ-UI-050 工具页不滚，只有组件内部滚（1.9.0）

- 目的：一块版面只有一套滚动语义。
- 背景（用户实测）：鼠标停在控制面板上滚不动、往旁边挪两像素又能滚整页。
  这两半里说得通的是前一半——控制面板本来就不该滚（REQ-UI-034）。既然如此，
  该退场的是外面那一层。
- 要求：页面不得有页面级滚动。全仓唯一一处在 `ComponentGalleryView`（已随该类一并删除）。
- 要求：包边这一层 `ClipToBounds`。装不下时**裁掉**，不是长出去也不是长出滚动条。
  裁切是有意让「装不下」变成看得见的事故；滚动条会让一个排版错误一直活着，
  而且活得很舒服——没有人会去修一个「滚一下就能看到」的版面。
- 要求：滚动只发生在组件内部。表格与泳道自带视口，靠顺序容器分给它们星号行

  `PART_ContentHost`，下拉框弹出层也有一个。判据是 `TemplatedParent == null`
  再排掉自带视口的组件（白名单）。按「祖先里有没有表格」判会把输入框报成违规，
  **一个连输入框都容不下的规则不会有人遵守**。
- 范围：本版只适配自持页面。模块页由渲染器交出的树本来就没有页面级滚动，无需改动。

  - 「填入控制台」只保留命令集的行操作一处，详情页不再重复放一个按钮。

## REQ-UI-054 `view` 是一条空转声明，暂不实现也不删（1.9.0，已记账）

- 目的：把一个已查实的缺陷记在案上，而不是让它继续以「已支持」的样子活着。
- 事实：`PageViewOptions`（`view.filterable` / `sortable` / `selection`）在 schema 里声明、
  在 `PageDescriptionReader` 里解析，**全仓没有任何一处读它**。`AuroraTable` 里

- 本版处置：**不实现**（实现筛选排序是给组件加能力，与本轮「组件保持克制」相悖），

  1.9.0 新增的三页描述**一律不写 `view`**，不给死字段续命。
- 未决：实现还是删除，需要在下一版拍板。实现的收益是所有表格一起受益且
  §2.4 的承诺兑现；删除的收益是 schema 不再说谎。两条都比现状好。
- 验收：本条无门禁，故意的——它是一张欠条，不是一条已完成的要求。

## REQ-UI-055 取数占位符判「有没有行」，不判「值是不是空」（1.9.0）

- 目的：让**筛选**用的通道值可以为空，而**选择**用的通道仍然能说「还没选」。
- 背景（1.9.0 改造时当场撞上）：控制面板的文本框在页面打开时就会把初值发上通道
  （REQ-UI-045），而初值通常是空串。取数把「空串」当成「取不到值」的话，

- 说明（这是把两处口径对齐）：动作那一侧 `ActionRegistry.BuildCommandText`

- 关联组件：`b-Code-Studio/Shell/2-Components/Pages/PageRenderer.cs`
- 关联验证：`VERIFY-HOSTED-PAGES`

## REQ-UI-056 弹出层可以接到页面右键上（1.9.1）

- 目的：让低频编辑器**连一个按钮都不占**，而不是只做到"不常驻一整块面板"。
- 背景（用户实测，Mercury 扩展坞管理页）：这一页顶上常驻着「加入扩展坞」面板
  （一个输入框加四个按钮）。它一周也用不到一次，而这一页真正要看的是下面那张条目表。
  REQ-UI-050 之后页面不滚，**被它挤掉的高度就是看不见的行**——版面不再是审美问题。
  弹出层（REQ-UI-012）本来就是为这个问题造的，但它自带一个按钮，仍然占一行。
- 要求（不新建组件）：浮层本体沿用 `AuroraFlyout`，只多一条打开它的路。
  右键那条**不是**另一个组件——再写一套的话，两份浮层的圆角、阴影和收起时机会各走各的，
  而那种差异浅色下几乎看不出来（组件区第 1 条规矩）。
- 要求（先查再建）：本条落地前先查了仓里已有的右键实现——表格行操作菜单
  （`AuroraTable.BuildContextMenu`）、轮换选项框的候选菜单、控制台的复制菜单。
  三处都是**动作菜单**，放不进输入框，因此都不能直接改用；能复用的是浮层本体，
  而它缺的只是一个触发方式。
- 要求（接的是整页，不是那一格）：`trigger: "context"` 的浮层由 `PageRenderer.Render`
  在整棵树建完之后挂到页面根上。声明的位置对它没有意义——它要接的是"这一页的右键"。
- 要求（同一页只接一个）：右键只有一次。接第二个的话"弹出哪一个"取决于建页顺序，
  而那个顺序不受任何东西保证——与选择通道的抢注规则同一条理由。第二个渲染成写明原因的牌子。
- 要求（右键落点必须命中得到）：渲染器自己包一层**透明底**的容器。`Panel` 的
  `Background` 为 null 时空白处不参与命中测试，而空白处正是这条路唯一会被右键到的地方。
  不能直接往 root 上写底色：root 可能就是某个组件本体（只有一张表的页面），
  从外面覆盖它的底色等于改组件的外观（DEC-005 的反面）。
- 约束（**浮层不能收成 `Collapsed`**）：WPF 的 `Popup` 在不可见的父级下**开不出来**，
  且不抛异常、不触发 `Closed`——`IsOpen` 写进去就是 `false`，症状是"右键完全没反应"。
  门禁里实测过：同一段代码，父级可见时 `IsOpen=True`，`Collapsed` 时 `IsOpen=False`。
  因此浮层本体挂在页面根那一层并靠内容定尺寸（按钮已 `Collapsed`，内容尺寸为 0），
  它声明的那一格则留一个真正 `Collapsed` 的空位——顺序容器会给每个子节点补一段间距，
  零尺寸的元素照样留下那段间距，而 `Collapsed` 的元素连边距都不参与。
- 约束（与行操作菜单的关系不需要协调）：订阅**冒泡**的 `MouseRightButtonUp` 且不收
  已处理的那些。表格在行上弹自己的菜单并把事件标成已处理；在空白处它主动放弃
  （`OnRowContextMenuOpening` 判无行即取消），事件继续往上冒。
  于是"右键行 → 行菜单、右键空白 → 浮层"是自然结果，不是谁去让着谁。
- 说明（这条能力有代价，写进用法文档）：版面上没有任何东西提示"这里右键有内容"。
  它只适合"页面上本来就有别的东西可看"的低频编辑器；是主操作就该留按钮式。
- 验收：`PopupTriggerContractTests` 六条。
- 关联组件：`b-Code-Studio/Shell/2-Components/Widgets/AuroraFlyout.cs`、
  `b-Code-Studio/Shell/2-Components/Pages/PageRenderer.cs`
- 关联验证：`VERIFY-POPUP-TRIGGER`

- 目的：让「界面自己漏接了一根线」当场说出来，而不是画成一张空表。

## REQ-UI-060 控制面板的行是一等结构（1.9.2，破坏性）

- 目的：让「哪几个元素是一行、这一行的余量怎么分」在声明侧说得出来。
- 背景：1.9.2 之前面板有**两套互不相干的排版**，由 `orientation` 二选一。
  竖排是一个三列共享的 Grid：每个控件独占一行，行行对齐得像张表，不换行；
  横排是统一列宽的自动换行面，所有元素被拉成同一个宽度，一行放几个由可用宽度决定。
  两套都表达不了「这三个是一行、那一个自己一行」——竖排里行是 `inline` 的副产品，
  横排里行是宽度算出来的结果。用户在 Janus 的项目操作面板上直接撞到：
  三行本来没有对齐的理由，而对齐的代价是最长的那个按钮把另外两行的输入框一起挤窄。
- 要求（协议 V3，破坏性）：`widgets` 换成 `rows`，每行 `{ mode, widgets }`。
  `orientation` 与 `inline` 一并退役。**不留兼容分支**：两种写法并存的话，
  「这份声明按哪一套排」会取决于有没有写某个字段，而那正是这一版要消灭的东西。
- 要求（最窄宽度）：每个元素先有一个最窄宽度。按钮与说明文字按字宽量出来，**不必注册**；
  文本框量不出来（空框的内容宽度是 0），因此按声明的 `minWidth`，没写就取 120。
  按内容量出来的值封顶 260——一段长说明的「自然宽度」可以是几百像素，
  拿它当最窄宽度会让整行判成放不下，而它本来是可以换行的。
- 要求（放得下就不换行）：一行的元素按最窄宽度加起来还装得进可用宽度时**不折行**，
  余量按这一行的模式分掉。
- 要求（两种模式）：`even` 均布——余量按最窄宽度**等比放大**，宽的还是宽、窄的还是窄；
  `flex` 可变（缺省）——其余各自停在最窄宽度，余量全给声明了 `flex` 的那一个，
  一个都没声明时是**最右边**那一个（既有面板的样子）。
  一行写了两个 `flex` 只认第一个：拒绝整份声明太重，而「两个都变宽」没有一种分法说得出道理。
- 要求（折行不产生新的行）：放不下时折成多个视觉行，**而折出来的仍然是同一个声明行**——
  每个视觉行各自按母行的模式分配余量，行与行之间那条横分隔线不会因此多一条。
  折行是宽度不够时的应对，不是版面结构的变化；让它变出一条分隔线，等于让窗口宽度去改声明。
- 要求（标签是独立的一个元素）：文本框的标签自己占一格，参与最窄宽度的计算，
  并因此在它与输入区之间落下一条渐隐竖线。面板里的控件不带边框，
  那条线是「这是标签、那是输入区」唯一的分界。标签为空时不放这一格——
  空标签会画出一条紧贴左边、两侧什么都没有的线。
- 要求（分隔线仍然是画出来的）：行内相邻元素之间画竖线，声明行之间画横线，两端渐隐。
  **不做成子元素**：位置只有排完版才知道，做成子元素就得先假设一个位置，
  折行处于是会冒出一条贴着行首的线。`Aurora.Panel.Divider` 随之删除——
  留一份没人用的样式，下一个人只会照着它再摆一条子元素回去。
- 要求（`required` 退役）：面板的必填校验是**全局**的——任何一个必填框为空，
  面板上每个按钮都拒绝执行。Janus 因此一直不敢用它（注释在案），
  Mercury 三个数字框全写了 `required` 却共用同一批按钮，等于把整块面板锁在
  「三个都填了」上。参数缺失交给各条指令自己的 `Required` 去报，报出来的还是那条指令的话。
- 要求（接口一并收窄）：`PanelView.ControlIds` 收成 `internal`——它不是面板对外的能力，
  是 `aurora.ui.panelset` 一句错误信息的素材；`AuroraPanelBoard` 的
  `MinItemWidth` / `MaxItemWidth` / `ColumnGap` / `RowGap` 四个可写属性改成常量，
  全仓零处赋值，而「看起来可调」本身就是个错误信号。
  排版面对外只留一份版面快照 `CellBounds` 供门禁断言：均布、可变、折行三条规则的效果
  全都是「谁多宽、在哪儿」，一份快照够所有断言用，每加一条规则不必再多一个口子。
- 说明（留待下一轮）：`PanelDefinition` 的 `side` / `ratio` / `visible` 三项
  只在面板作为独立可停靠窗口时有效，页面内嵌的 `panel` 节点不读它们。
  本轮只在注释里写明，没有拆成两个类型——拆会牵动 `PanelManager`、
  `BuiltinCommands.Panel` 与面板 JSON 配置，而收益只是少三个被忽略的字段。
- 影响面（消费侧同步改）：Aurora 自持四页、Janus 四个面板、Mercury 两个面板。
  三个仓的声明全部改写，没有一处留在旧形状上。
- 验收：`PanelComponentContractTests` 十七条，其中
  `RowWrapsOnlyWhenItCannotFitAndStaysOneDeclaredRow`、
  `WrappedLinesKeepTheParentRowMode`、`EvenRowScalesEveryCellProportionally`、
  `FlexRowGivesTheRemainderToTheDeclaredElement`、`FlexDefaultsToTheRightmostElement`、
  `LabelOccupiesItsOwnCellNextToTheControl` 是这一版的核心判据；
  `SelectionChannelContractTests.ControlsInOneDeclaredRowShareOneVisualLine`。
- 关联组件：`b-Code-Studio/Shell/2-Components/Widgets/AuroraPanelBoard.cs`、
  `b-Code-Studio/Shell/2-Components/Panels/PanelView.cs`、`b-Code-Studio/Shell/2-Components/Panels/PanelDefinition.cs`
- 关联验证：`VERIFY-PANEL-ROWS`

## REQ-UI-062 表格列可以拖着换顺序，且记得住（1.9.2）

- 目的：把很早以前有过、后来随表格统一实现一起丢掉的那个能力接回来。
- 要求（一律可拖，不按声明开）：`GridView.AllowsColumnReorder` 全表打开，

- 要求（星号列钉在最右）：占满剩余宽度的那一列不在最后就没有「剩余」可占。
  拖它、或者把别的列拖到它右边，都会让它当场被拨回最右——**一条规则盖住两种拖法**，
  分开写的话总有一种拖法两边都没管到。
- 要求（修正必须排到下一拍）：这是 `ObservableCollection` 的通知过程中，
  在处理器里再动一次集合会抛「不允许重入」。
- 要求（宽度分摊改按可视顺序）：`ApplyColumnWidths` 里「最后一列吃余数」说的是
  屏幕上最右边那一列。列可以拖之后，照声明顺序算会把余数发给一列画在中间的列，
  右边就空出一条缝。
- 要求（记得住）：列序按「模块/页面/节点」记进设置，跨重启仍在。
  **整本账是一个设置键**，不是一张表一个：表的身份数量随模块增长没有上界，
  一张表一个键会让设置文件被这类条目淹掉，且没有任何一处能把它们一起清掉。
  没有节点 id 的表不记——那样的表拖完也认不出是哪一张。
- 要求（只记顺序，不记宽度）：宽度是声明的权重按页面宽度算出来的结果（REQ-UI-039），

## REQ-UI-002 组件库承接与家族完整性（规划中）

- 目的：Aurora 承接的不只是「几个页面」，还有一套**已在被三个模块使用**的组件库。
  它决定了模块作者能否长期不碰颜色、不碰模板地做界面。
- 背景（2026-08-19 实测，依据见 `../history/前端组件计划表V1.0.md`）：
  宿主 `Themes/` 现有 2,044 行，其中 `ShellControls.xaml` 1,001 行提供 16 个具名样式，
  `ShellTokens.xaml` 提供 65 个令牌。Janus / Mercury / Minerva 合计引用 30 个不同的
  `Shell.*` 键。Mercury 的两个页面**零自造样式**——现有库足以支撑列表 + 详情类主力页面。
- 要求（键名整体改为 `Aurora.*`，DEC-005）：承接时把 65 个令牌与 16 个具名样式的键
  从 `Shell.*` 改为 `Aurora.*`，家族结构不变（`Aurora.Brush.*`、`Aurora.Button.*`、
  `Aurora.Segment.*` …）。**不得提供 `Shell.*` 别名、不设弃用期、不做双键并存**——
  别名会让每个组件维护两套键、每次演进同步两处，且无法判断模块实际用的是哪一套。
- 要求（资源文件同步改名）：主题文件随键名一起改，不留 `Shell` 字样——
  `ShellTokens.xaml` → `AuroraTokens.xaml`、`ShellTokens.Dark.xaml` → `AuroraTokens.Dark.xaml`、
  `ShellControls.xaml` → `AuroraControls.xaml`、`ShellDocking.xaml` → `AuroraDocking.xaml`、
  `ShellChrome.xaml` → `AuroraChrome.xaml`、`ShellToolTips.xaml` → `AuroraToolTips.xaml`。
  文件名与键名不一致本身就是下一个人要花时间确认的坑。
- 要求（模块不得自建组件，DEC-005）：模块 XAML 中**不得出现 `Style x:Key=` 与
  `<ControlTemplate>`**；颜色、字体、尺寸、控件外观一律取自组件库。该禁令的前提是
  组件库先补齐缺件，见下条。
- 要求（家族完整性，解禁前置）：组件按**家族**维护，不按单点补丁。缺成员时补齐该成员，
  不接受「模块自己造一个」作为长期状态。当前唯一已知缺件：分段家族有
  Bar / Divider / Label / TextBox / ComboBox / Button / CheckBox 七个成员，
  **缺 RadioButton / Toggle**，Janus 因此自造 40 行 `OperationSegment`。
  **`Aurora.Segment.Toggle` 未落地前不得对模块执行自建禁令**——先断人后路再补路，
  只会逼出更难发现的绕行写法。
- 要求（静默退化必须可查，DEC-005 的代价对冲）：`DynamicResource` 找不到键时 WPF
  **不抛异常**，只是不套用该值。模块在适配前不会崩，而是静默退化成 WPF 默认外观。
  因此必须提供一个可执行检查器，扫描给定路径下的 XAML 并报告：
  ① 残留的 `Shell.*` 引用；② 自建的 `Style x:Key=` / `<ControlTemplate>`；
  ③ 字面颜色（`#RRGGBB`、`Colors.*`）。检查器要能对**模块仓**运行，使「哪些模块尚未适配」
  成为可查询事实，而不是靠肉眼发现哪一页变丑。
- 要求（表格技术选型）：表格能力围绕 `ListView` + `GridView` 建设。实测 12 个页面里
  ListView 用 21 次、GridViewColumn 46 次，`DataGrid` 仅 2 次——`DataGrid` 不纳入主题化范围，
  避免维护两套表格外观。
- 要求（资源引用方式）：一律 `DynamicResource`。`StaticResource` 在主题切换后不更新，
  且键名重构期间它会在**编译期**就失败——两种失败模式混在一起会让排查更难。
- 验收：承接后 `Themes/` 内不存在任何 `Shell.` 前缀的键（含注释外的字符串）；
  检查器对三个模块仓运行，输出的待适配清单与实际情况一致；
  `Aurora.Segment.Toggle` 落地后 Janus 可删除自造模板且外观不变（浅色与深色各一次目视核对）。
- 关联组件：`Themes/`（`AuroraTokens.xaml` / `AuroraControls.xaml` / `AuroraDocking.xaml`）
- 关联验证：`VERIFY-UI-TOKENS`（承接时建立）
- 现行令牌表与嵌入页结构：[HistoryAurora_UI风格与嵌入页面规范.md](HistoryAurora_UI风格与嵌入页面规范.md)

## REQ-UI-007 表格组件（1.6.0）

## REQ-UI-009 按钮绑动作，不绑指令（1.6.0）

- 目的：消灭「模块改了指令名，按钮静默变哑」这一类缺陷。
  它的特征是：点了没反应、没有报错、也没有任何地方记下这件事。
- 要求（协议）：模块以 `<域>.ui.actions` 返回动作声明 JSON（schemaVersion 1，
  含 `id` / `title` / `command` / `args` / `danger` / `summary`）。
  Aurora **主动拉取**，与页面描述同一模型；宿主只路由，不解释载荷。
- 要求（谁记住什么）：按钮记住的是**动作 id**，指令名归模块自己的声明。
  模块改指令名只需改自己那一行，面板 JSON 与页面描述一个字不动。
- 要求（不静默）：动作解析不到时**必须显示原因**。面板按钮渲染成写着原因的警示牌，
  而不是一个禁用按钮——"看起来能点但其实不能"并不比"点了没反应"好。
- 要求（断链可查）：声明了却指向注册表里不存在的指令，进"断链"账，
  `aurora.ui.actions` 可查。这让原本要等用户点下去才暴露的事实提前成为可查询状态。
- 要求（现取不固化）：点击时**现取**声明，不在构建时把指令名固化进闭包——
  模块热重载后固化的那份就是下一个"点了没反应"。
- 要求（占位符）：`args` 的值可含 `{控件id}`，由 Aurora 用同面板控件当前值替换。
  引用不存在的控件时整条拒绝执行，不把 `{x}` 原样发上总线——那会变成一条参数明显错误、
  却"执行成功"的指令。
- 要求（页面按钮）：页面描述的 `invoke` 支持 `action`（推荐）与 `command`（兼容）。
  用 `command` 的按钮渲染时记一条 Warn，使"哪些按钮还没换成动作"是可查的事实，
  而不是某次代码走查的印象。
- 验收：`ActionDeclarationContractTests` 全绿；`aurora.ui.actions` /
  `aurora.ui.reloadactions` / `aurora.ui.invoke` 已注册。
- 关联组件：`b-Code-Studio/Shell/2-Components/Actions/`、`BuiltinCommands.Actions.cs`
- 关联验证：`VERIFY-ACTION`

- 目的：把泳道的**布局与绘制**从 HistoryJanus 收回 Aurora。此前 Janus 的

## REQ-UI-018 aurora.ui.invalidate 归一 owner 与域（1.7.0）

- 现象（需求书 §二之二 D1，Mercury 2026-08-25 部署时实测）：

  （`ModuleDomainNaming.ToDomain` → `ModuleCommandProbe.ExpectedOwner`）。

## REQ-UI-022 控件字典按线程缓存（1.7.1）

- 背景：1.6.0 的 `AuroraComponentResources.Ensure` 每个组件各
  `new ResourceDictionary { Source = … }` 一次。按 URI 解析资源依赖 WPF 的应用级资源上下文，
  而模块被装进可回收 ALC、入口程序集又不是本程序集——那个上下文并不是任何时候都成立
  （门禁里实测：一条干净 STA 线程上第一次按 URI 取字典会抛

## REQ-UI-023 ~~浮窗拖动必须交回标题栏拖动~~（1.7.2，**已作废，见 REQ-UI-026**）

- 现象：1.7.1 之后**仍然**叠不回去，蓝色停靠指示一次都不出现。
- 成因（这才是根因，REQ-UI-019 只补了前提条件）：Aurora 自己接管了浮窗页头的拖动——
  `HandlePaneMouseLeftButtonDown` 认出页头在浮窗里，就走
  `BeginHostWindowGesture` → `TryDragWindow` → `Window.DragMove()`。
  `DragMove()` 发的是 `WM_SYSCOMMAND/SC_MOVE`；而 AvalonDock 的
  `LayoutFloatingWindowControl.FilterMessage` 只在收到
  `WM_NCLBUTTONDOWN` + `HTCAPTION` 时才创建 `DragService`——

- 为什么拖出去一直好用：那一半是 AvalonDock 自己的 `AttachDrag` 做的，
  它在收到 `WM_ACTIVATE` 后**自己** `SendMessage(hwnd, WM_NCLBUTTONDOWN, HTCAPTION, …)`。
  所以我们这次用的不是绕过它的偏方，就是它自己的那一招。
- 要求：拖动目标是 `LayoutFloatingWindowControl` 时，不用 `DragMove()`，
  改为释放捕获后向该窗口发 `WM_NCLBUTTONDOWN`/`HTCAPTION`；拿不到句柄时退回 `DragMove()`。
- 验收：**只能真机确认**——需要真实的 Win32 移动循环，自动化里驱动不了。

- 关联验证：`VERIFY-FLOAT-DOCKBACK`

## REQ-UI-026 浮窗拖动前必须放掉鼠标捕获（1.7.4）

- 现象：浮窗**只能拖出、叠不回去**，拖动时那组蓝色停靠指示一次都不出现。
  1.7.1 与 1.7.2 各改过一次，都没修好——两次的判断都建立在同一个错误前提上。
- **前两轮错在哪**（反编译 AvalonDock 4.72.1 后确认）：
  `LayoutFloatingWindowControl.FilterMessage` 只处理
  `WM_SYSCOMMAND`（0x0112，且仅 SC_MAXIMIZE/SC_RESTORE）、`WM_LBUTTONUP`（0x0202）、
  `WM_MOVING`（0x0216）、`WM_EXITSIZEMOVE`（0x0232）。
  **它不看任何非客户区消息**，`WM_NCLBUTTONDOWN`/`HTCAPTION` 根本不在其中。
  真正创建 `DragService`（也就是那组蓝色指示）的是
  `WM_MOVING → UpdateDragPosition`——已用反射直接调用验证：
  调一次 `UpdateDragPosition`，`_dragService` 与 `DockingManager._overlayWindow` 双双建起来。
  **也就是说 Aurora 这边的停靠机制本身是好的，缺的只是"窗口真的被系统移动循环拖着"。**
- 根因：`Window.DragMove()` 之前**没有放掉 Win32 鼠标捕获**。
  WPF 的 `Mouse.Capture` 底层就是 `SetCapture`；捕获还在时 `DefWindowProc` 的移动循环
  不会启动，`DragMove()` 于是静默地什么都不做——不抛异常、也不移动窗口，
  自然一条 `WM_MOVING` 都不发。
- 要求：拖动浮窗前 `Mouse.Capture(null)` **并** `ReleaseCapture()`，然后 `DragMove()`。
- 同时撤销：`WindowChrome.CaptionHeight` 回到 0（REQ-UI-019 作废）。
  抬高它有害——页头会变成非客户区，WPF 收不到鼠标按下，
  Aurora 自己那条会去调 `DragMove()` 的拖动手势根本起不来。
  发 `WM_NCLBUTTONDOWN` 的做法一并撤销（REQ-UI-023 作废）。
- 验收：`FloatingWindowChromeContractTests`（外观前提）+
  `ShellChromeContractTests.FloatingToolWindowHasNoSecondOuterChromeRow`。
  **拖放手感只能真机确认**：判断标准是拖着浮窗经过主窗体时那组蓝色方位指示出不出来。
- 关联验证：`VERIFY-FLOAT-DOCKBACK`

- 实测结论（2026-08-25，1.7.4 的代码）：**这条链路是通的**，五条断言全绿，
  连跑两次稳定。也就是说 `Mouse.Capture(null) + ReleaseCapture() + DragMove()` 的修法成立。
- 关联验证：`VERIFY-MOUSE-DOCK`

## REQ-UI-028 浮窗停靠链路必须自报断点（1.7.6）

**要求.** 浮窗拖动时，停靠链路的四个环节必须各自留下可观测的证据，并在拖动结束时
输出一条指明断点所在环的结论。四环为：

| 环 | 内容 | 观测手段 |
| --- | --- | --- |
| 1 | 系统移动循环启动 | `WM_ENTERSIZEMOVE` 计数 |
| 2 | 循环持续发位移消息 | `WM_MOVING` 计数 |
| 3 | AvalonDock 建立拖动服务 | `LayoutFloatingWindowControl._dragService` |
| 4 | 覆盖窗建立并显示 | `DockingManager._overlayWindow` 的可见性、模板、尺寸 |
| 5 | 覆盖窗里排布出了元素 | 停靠区数量、覆盖窗可视树元素数、具名投放件数、最终投放目标 |
| 6 | 屏幕上真的有像素 | 覆盖窗渲染成位图后的非透明像素数、主色、与主窗体的 Z 序 |

**理由.** 这条链路在门禁里是通的（REQ-UI-027 的鼠标冒烟每次都能合并），真机上却不出
停靠指示。差异只存在于真机环境，而真机不能挂调试器、更不能停宿主。此前两轮都是靠
推断改的——先猜 `CaptureHeight`（REQ-UI-019），再猜 `WM_NCLBUTTONDOWN`
（REQ-UI-023）——两次都错，两次都白发一版，最后靠反编译才定位到 REQ-UI-026 的
`ReleaseCapture`。**断点必须测出来，不能想出来**，这是本条的由来。

**约束.**

- 探针只读。不得写入任何 AvalonDock 状态，不得改变拖动行为；拖动结束即摘钩。
- 反射失败、句柄缺失只记一行警告，绝不允许探针本身让拖动出错。
- **不得用点采样判断"有没有发生过"。** 覆盖窗 `Show()` 之后 `IsVisible` 与尺寸要等一轮
  布局才更新，只读某一条 `WM_MOVING` 会把"尚未显示"误报成"显示不了"。1.7.6 首版就
  踩了这个坑：在能正常合并的链路上误报"断在第 4 环"，改成全程观测取最好状态后才
  报"四环齐全"。同样的坑在 1.7.5 写 `IsDragging` 轮询时已经踩过一次。
- **第 4 环通过不等于指示出现。** 覆盖窗建起来、有模板、尺寸正确，仍可能是一片空的：
  模板内容在可回收上下文里解析失败时，窗会照常显示。所以必须有第 5 环，数覆盖窗
  可视树里实际渲染出多少元素。1.7.6 只做到第 4 环，真机上得到"四环齐全"却仍无指示，
  正是漏了这一层。
- **数投放件要按 `x:Name` 找，不能按类型名找。** AvalonDock 的 `DocumentPaneDropTarget`
  之流是描述投放区的普通类，根本不在可视树里；树里那些按钮是 `Image`/`Grid`，只有
  名字带这个词。按类型名数会在能正常合并的链路上数出 0——这是第二次被正对照拦下的
  误报。
- **必须记"进没进过停靠区"，不能只记某一刻的坐标。** 浮窗起手时光标本来就在主窗体外，
  单点坐标只能证明起手在外面，证明不了后来有没有拖进去。1.7.7 真机日志给出
  `矩形=(279,476)+1280x795、光标=(1803,623)`，看似"光标在区外 244px"，实则那是起手瞬间
  的读数，对判断毫无用处。
- **命中测试用真实光标（`GetCursorPos`），不是 WPF 口径（`Mouse.GetPosition`）。** 实测：
  门禁那条能正常合并的链路上两者偏差最大 956px，WPF 口径全程没进过停靠区，合并照常
  成功。曾据此写过一条"移动循环里 WPF 鼠标位置陈旧"的结论分支，正对照当场证伪——
  真机上它必然触发，会把排查引向一个不存在的病。**探针里任何一条结论分支，都必须先在
  正对照上验证它不会误报。**
- **元素排布正常 ≠ 屏幕上有像素。** 真机实测覆盖窗 210 个元素、105 个可见、16 个具名
  投放件，全部大于门禁基线，用户截图里却一个指示都没有。`IsVisible` 与尺寸只证明元素
  被排进了布局。第 6 环因此必须把覆盖窗**渲染成位图数非透明像素**——这是唯一不依赖
  "模板长什么样"的测法。曾按 `Image.Source` 是否为空判断，门禁里覆盖窗图像=0（指示根本
  不是图片画的），结论沦为空转。
- **"画出来了"还要问"在不在上面"。** 覆盖窗画了像素却被主窗体压在 Z 序下方，看到的
  同样是"没有指示"。两者必须一起报。
- 结论文案必须直接指名断在第几环，并在第 4 环为 null 时附带停靠管理器的屏幕矩形与
  当前光标位置——多显示器或非 100% 缩放下 `PointToScreenDPI` 会把矩形算歪，命中测试
  因此落空，两个数字并排就能看出来。

**验收.** 见 `VERIFY-DOCK-PROBE`。正对照：在鼠标冒烟这条已知能合并的链路上，结论必须
是"五环齐全"，且基线为 `停靠区=2 覆盖窗元素=210 其中可见=80 具名投放件=12
最终投放目标=DocumentPaneDropTarget`。探针读不准比没有探针更糟——本条的三次误报
（点采样过早、按类型名数投放件、只做到第 4 环）全部是被这个正对照拦下的，所以它是
本条的硬性组成部分，不是可选步骤。

## REQ-UI-029 覆盖窗必须自带主题字典（1.8.0）

**要求.** AvalonDock 的覆盖窗（拖动浮窗时那组蓝色方位指示所在的独立 `Window`）必须像
浮窗与弹窗一样，由 Aurora 显式并入主题字典，不得依赖 AvalonDock 按 URI 自行解析。

**理由.** 这是 DEC-009「**能离开主窗体的东西，自带字典**」的遗漏项。覆盖窗是独立
`Window`，其画刷靠 `OverlayWindow.UpdateThemeResources` 按
`/HistoryAurora;component/Themes/AuroraTheme.xaml` 重新解析；而按 URI 解析依赖 WPF 的
应用级资源上下文，模块被装进可回收 ALC、入口程序集不是本程序集时并不总成立。

解析不到画刷时 **WPF 不抛异常**，只是不套用。真机 1.7.9 实测的形态正是如此：

| 观测 | 真机 | 门禁基线 |
| --- | --- | --- |
| 覆盖窗元素 / 可见 / 具名投放件 | 210 / 105 / 16 | 210 / 80 / 12 |
| Z 序（覆盖窗 vs 主窗体） | 45 vs 49（在上） | 18 vs 22（在上） |
| **渲染后非透明像素** | **0** | **1044 / 52250** |

元素排布、层级、命中测试全部正常，屏幕上一个像素都没有。

**做法.** 主题按**实例**下发：`AuroraTheme` 继承 `DictionaryTheme`，字典由
`ShellWindow.xaml` 以具名资源 `AuroraDockTheme` 在编译期解析（BAML 这条路在宿主里成立），
运行时只传实例。覆盖窗因此不需要解析任何 URI。

**约束.**

- **不得在拖动途中给覆盖窗并字典。** 并入会触发重新套模板、重建可视树，而 AvalonDock
  正在同一调用栈里遍历投放目标并对它们调 `PointToScreen`，直接抛
  `InvalidOperationException: 该 Visual 未连接到 PresentationSource`，测试宿主当场崩溃
  （实测）。且覆盖窗每次拖动结束即销毁，"这次补下次生效"也不成立。只能在构造前就备好。
- **"按 URI 重解析主题字典"必须一次找全。** 仓里原有两处：AvalonDock 给覆盖窗的那处，
  和 `ShellWindow.Chrome.LoadThemeResources`。只改前一处时，后者拿到空 URI → 窗格样式
  整个退回 AvalonDock 默认外观 → 页头布局变了、按钮位置都不一样，当场挂 9 条窗格契约
  测试。改主题下发方式必须同时覆盖两处。
- 令牌随主题切换，仍从容器继承，不在覆盖窗上钉死。

**验收.** 见 `VERIFY-DOCK-PROBE`：真机拖动后 `覆盖窗实绘像素` 须大于 0。修复前后的判别
数据是 `覆盖窗字典`——门禁基线为 1，真机若为 0 即坐实本条。

## REQ-UI-030 页面数据源不得阻塞建页线程（1.8.3）

**要求.** `table` 与 `swimlane` 的 `dataSource` 只在对应组件首次 Loaded 后启动一次；模块命令
必须在线程池执行，Aurora 只在结果返回后回到 UI 线程更新组件。Render、窗口登记和初始布局期间不得
同步进入模块取数命令。

**理由.** 模块命令可能在第一次异步挂起前执行同步磁盘或 Git 工作。渲染器若在构造组件时直接调用，
模块实现细节就会进入宿主建页调用栈，表现为部署后整个前端卡死。不可见页面也不应提前消耗取数成本。

**验收.** 见 `VERIFY-PAGE-DATA-LIFECYCLE`。

## REQ-UI-063 关闭时独立保存窗口位置台账（1.10.0）

**要求.** 退出或隐藏前端时，布局 XML 写入失败不得阻止 `layout.placements` 保存。窗口的隐藏状态、
停靠方位、比例、标签目标与中央页顺序必须继续落入设置服务；下一次启动按该台账恢复。

**理由.** Aurora 作为不可固定的模块装载时，AvalonDock 类型可能来自可回收 AssemblyLoadContext，
`XmlLayoutSerializer` 会拒绝序列化。若把 XML 与位置台账放在同一个 `try` 中，序列化异常会让关闭后的
隐藏/停靠状态静默丢失。

**验收.** 见 `VERIFY-CLOSE-PERSISTENCE`。

## REQ-UI-064 页签拖动显式进入浮窗拖动循环（1.10.0）

**要求.** 页签拖动越过系统阈值后，Aurora 必须显式执行浮动并继续 `DragMove`；不得依赖自定义页签模板
是否仍触发 AvalonDock 的默认拖动处理。浮窗进入系统移动循环后，应出现蓝色停靠覆盖层，松手可合并到目标
文档/标签组。

**理由.** Aurora 替换了 AvalonDock 页签模板。默认拖动事件可能在模板边界处被吞掉，导致只记录待浮动状态、
既不创建浮窗也不触发 `WM_MOVING`，用户看到的就是没有蓝色标记且无法合并。

**验收.** 见 `VERIFY-TAB-DRAG-FLOAT`；蓝色覆盖层和真实鼠标移动循环需在真机确认。

## REQ-UI-065 拖动会话单一所有者与竞态封闭（1.11.0）

**要求.** 普通页签、专注页签、浮窗页头和主窗标题的拖动必须共享一个内部会话状态机与窗口拖动驱动器。
页签越过阈值时必须先保存会话和光标信息，再释放 WPF/Win32 捕获并经 Dispatcher 创建浮窗；浮窗创建后只能由
统一驱动器激活、释放捕获、启动 `DragMove` 和停靠探针。提前松手、命令失败、超时、捕获丢失和会话被取代都必须
幂等结束，不得静默遗留捕获或劫持后续拖动。

**理由.** 分散的页签/浮窗拖动状态会让阈值事件依赖光标仍在 DockManager 内，并在异步浮窗创建期间丢失左键状态；
`DragMove` 未进入真实 Win32 移动循环时，蓝色停靠覆盖层和最终合并会同时消失。单一所有者和源码门禁可防止后续
代码改动重新增加旁路。

**验收.** 见 `VERIFY-DRAG-SESSION`、`VERIFY-TAB-DRAG-FLOAT`；源码门禁必须确认 `DragMove`、`Mouse.Capture(null)` 和
`ReleaseCapture` 只出现在 `WindowDragDriver`。

## REQ-UI-066 描述式来源与开关组件（1.12.0）

控制面板必须提供 `switch` 和 `sourcePicker` 两种通用组件。开关点击立即以动作参数 `{value}` 提交；来源选择器
单击可编辑文本，回车或失焦提交，双击执行声明的文件/目录选择命令并在成功后自动提交。普通 `textbox` 可通过
`commitAction` 复用相同的回车/失焦提交能力。模块页面不得自建控件或注册页面，页面分支统一由 Aurora `switch` 描述。

**验收.** 面板协议校验覆盖控件字段、动作参数替换和资源样式；Minerva Smoke 验证四个转换分支、选项顺序、
来源控件类型及状态摘要表移除。

## REQ-UI-067 页面停靠完整布局使用纯数据快照（1.12.20）

**要求.** 当前布局写入 `%AppData%\HistoryVulcan\layout\layout.v1.json`。格式是 Aurora 自有、带
`schemaVersion=1` 的 JSON，只保存稳定页面 ID、嵌套分栏方向与尺寸、页签顺序与选中项、自动隐藏组、
浮窗集合与 DIP 几何，以及隐藏位置台账；不得保存 WPF 活对象、程序集限定类型名或 AvalonDock 类型。

**恢复.** 已注册页面按 ID 重建原拓扑；存档中已经不存在的页面跳过，当前版本新增页面按默认声明补入。
尚未注册的模块页保留其方位、比例、标签目标、中央顺序和隐藏状态，注册到达后再认领。未知版本、损坏 JSON、
重复页面 ID、缺少中央主文档区或非法尺寸均告警并回退 `layout.placements`，再回退默认布局。离开所有显示器的
浮窗回到当前主工作区，仍在虚拟桌面内的浮窗仅做边界收敛。

**写入与聚焦.** 文件必须同目录临时写入、刷新到磁盘后原子替换；失败保留上一份有效快照，且不得阻止
REQ-UI-063 的 `layout.placements` 独立保存。聚焦期间保存使用聚焦前快照；还原仍装回同一棵 `LayoutRoot`，
只重建被 AvalonDock 判失效的浮窗模型。

**停靠回归边界.** 本要求不得修改 `AuroraOverlay.xaml`、`DockingDragProbe`、
`DockingOverlayResourceRepair`、`WindowDragDriver` 或拖动会话状态机。1.12.14 的蓝色方向控件、40 DIP
命中区、28 DIP 图形、透明预览框和只读探针继续作为发布门禁。

**验收.** 见 `VERIFY-DOCK-LAYOUT-PERSISTENCE`、`VERIFY-DOCK-OVERLAY-SEPARATED-HIT-ART` 与
`VERIFY-MOUSE-DOCK`。

## REQ-UI-068 表格单元格动作（1.13.0）

页面表格列可以声明 `cellAction` 动作 id。非空单元格必须渲染为真正的按钮，支持鼠标、Enter 和
Space；悬停显示动作说明。触发时必须携带被点击行，动作参数占位符默认从该行同名字段解析，不得改读
当前选中行。动作缺失或断链时表格仍显示，但上方必须出现可见诊断并写入日志；空单元格不得触发动作。

**验收.** 见 `VERIFY-TABLE-CELL-ACTION`。

## REQ-UI-069 通用选择弹窗（1.13.0）

`aurora.ui.dialog` 增加 `kind=choice`，候选必须是非空 `{label,value}` JSON 列表。弹窗显示 label、
成功结果返回 value，支持长列表滚动、键盘选择、确认、取消和双击确认。畸形、空列表或缺少 label/value
必须在打开窗口前返回明确错误，不得显示一个无法完成的空弹窗。

**验收.** 见 `VERIFY-DIALOG-CHOICE`。

## REQ-UI-070 面板按钮受控图标（1.13.0）

面板按钮可以声明 `icon` 语义名。图标几何由 Aurora 自持，模块不得提交 SVG、Path 或任意资源键；
首个且本版唯一支持项为 Lucide 语义的 `refresh-cw`。未知图标或在非按钮组件上声明图标时整份面板按
既有规则拒绝，并报告可见错误。未声明 `icon` 的旧按钮内容与样式必须保持兼容。

**验收.** 见 `VERIFY-PANEL-ICON`。
