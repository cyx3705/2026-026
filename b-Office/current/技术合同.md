# HistoryAurora 技术合同

本文件记录现行要求。每项要求有编号、目的、可验证的要求条目和验收方式。

当前源码为 **0.1.0**，骨架阶段。消费的宿主版本由 `b-Code-Studio/AuroraVersion.props` 的
`MinimumHistoryVulcanVersion` 单点声明，当前为 **3.13.0**。

## REQ-MOD-001 模块形态与宿主契约（0.1.0）

- 目的：本模块必须是一个可被 HistoryVulcan 装载的标准模块，不得自带第二套基础设施。
- 要求：产出单一程序集 `HistoryAurora.dll`，随 `module.manifest.json`
  （`type = HistoryVulcan.Module`、`ui = true`、`mcpExposure = readonly`）发布。
  实现 `IModuleContextAware`，由宿主在装载时注入 `IModuleContext`；命令一律经上下文注册，
  受 owner 回收。不得自行组装命令总线、日志或设置服务。
- 要求：引用宿主运行库一律 `Private=false`（部署时由宿主提供）。`b-Code-Verify` 下的测试
  工程是独立宿主进程，必须 `Private=true` 复制私有副本。
- 要求：消费的宿主版本只在 `AuroraVersion.props` 声明一次，发布脚本与门禁从此读取，
  不得各自硬编码字面量。
- 验收：`ModuleSmoke` 能在测试宿主中装载本模块并取得上下文；`dotnet build` 与
  `Test-QualityGate.ps1` 通过。
- 关联组件：`b-Code-Studio/Module`、`b-Code-Studio/AuroraBusinessComposition.cs`
- 关联验证：`VERIFY-BUILD`、`VERIFY-MODULE-LOAD`

## REQ-UI-001 承接宿主前端能力（规划中，尚未实施）

- 目的：让 HistoryVulcan 只保留指令总线与 MCP，把界面能力移出宿主进程。
- 背景（3.13.0 实测）：`vulcan` 域 81 条命令中 39 条来源为 `frontend:HistoryVulcan.Frontend`
  （ui 21、log 10、app 4、command 4），其 `PolicyVisible` 全为 false，零条投影为 MCP 工具。
- 要求（迁入时逐组细化）：每迁入一组能力，必须在本文件补一条带编号的子要求，写明
  迁入的命令清单、宿主侧对应命令的退役版本，以及两侧不得同时注册或同时缺失的对齐方式。
- 要求：迁入不得改变命令名。消费方看到的 `vulcan.ui.*` / `vulcan.log.*` 等名称保持不变，
  变的只是注册方。
- 验收：迁入后宿主侧该组命令消失、本模块侧出现，且 `vulcan.command.list` 的总数不变；
  MCP 可见工具数不变（这 39 条本就零投影）。
- 状态：**未开始**。骨架阶段 `Attach` 不注册任何命令。
- 关联验证：`VERIFY-COMMAND-PARITY`（迁入首组时建立）

## REQ-REL-001 发布真值与不可变性（0.1.0）

- 目的：区分可编辑源、当前候选与历史归档。
- 要求：`z-Publish/` 根部保存当前候选，`z-Publish/history/<发布标识>/` 保存不可变归档。
  两者都纳入 git，任何忽略或排除规则不得触碰 `z-*`。
- 要求：不直接编辑 `z-Publish/` 内容；修改权威源后经 `Build-HistoryAuroraPackage.ps1` 生成。
- 验收：`Test-QualityGate.ps1` 检查 `z-Publish` 未被忽略规则覆盖。
- 关联验证：`VERIFY-QUALITY-GATE`
