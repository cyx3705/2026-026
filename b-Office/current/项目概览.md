# HistoryAurora 项目概览

## 定位

HistoryVulcan 的宿主前端界面模块，编号 2026-026。名字取自罗马黎明女神 Aurora——本模块是
宿主对用户可见的那一面：窗口、布局、控制台与主题。

本模块不是独立应用。宿主合同以 `../2026-023-HistoryVulcan/b-Office/package/` 为准，本仓不复述。

## 体系位置

OneHistory 体系此前含 5 个项目（Diana 019、Janus 020、Mercury 021、Vulcan 023、Minerva 024）。
HistoryAurora 是第 6 个，也是第一个专职承载宿主界面的模块。

## 当前状态

**0.1.0 骨架阶段。** 目录结构、工程文件、门禁与文档骨架就位，`AuroraBusinessComposition.Attach`
尚不注册任何命令。没有任何前端能力已经迁入。

## 要解决的问题

HistoryVulcan 3.13.0 实测：`vulcan` 域 81 条命令中 39 条由前端进程注册
（`frontend:HistoryVulcan.Frontend`），构成为 ui 21、log 10、app 4、command 4。
这 39 条的 `PolicyVisible` 全为 false——**零条投影为 MCP 工具**，却占着服务进程注册表
近一半条目，并参与每次 schema 导出与目录快照。

把它们迁到本模块后，宿主可以只保留指令总线与 MCP，而 MCP 工具面一个不少。

## 迁移策略

按能力分组推进，由低耦合到高耦合：

1. `log.*`（10 条）——控制台过滤、级别、导出，与宿主状态耦合最浅
2. `ui.*`（21 条）——窗口、停靠、布局、面板，依赖 AvalonDock 封装
3. `app.*`（4 条前端侧）——主题、窗口状态、关于、打开数据目录
4. `command.*`（4 条前端侧）——帮助、历史、脚本执行、复制示例

每组迁入前先在 `技术合同.md` 立一条带编号的要求与验收方式，再落代码。宿主侧对应命令的
退役必须与本仓迁入在同一版本线内对齐，避免出现两处都注册或两处都没有的中间态。

## 尚未决定

- 迁移期间宿主与模块同时提供同名命令时的优先级与去重方式
- 界面模块是否需要独立的布局持久化，还是继续复用宿主的 `layout/`
- `command.run`（脚本执行）是否属于界面职责，或应归宿主指令总线
